# Architectural Decision Records (ADRs)

---

## ADR 01: Decentralized LXC Model vs. Monolithic Docker Host
* **Decision:** Deploy services as native, individual Linux Containers (LXCs) on Proxmox.
* **Rationale:** Fault Isolation, Resource Overhead reduction, and native backup granularity.

---

## ADR 02: Bare-Metal .NET 10 & Systemd vs. Docker Containerization
* **Decision:** Host .NET 10 Blazor applications natively on Debian LXCs running as `systemd` daemons.
* **Rationale:** Eliminates Docker engine overhead and simplifies CI/CD.

## ADR 03: App-Owned Blob Storage Abstraction (IBlobStore)
* **Decision:** Define an application-owned `IBlobStore` interface with two implementations selected at startup by `BlobStorage:Provider` (`local` | `s3`, default `local`): `LocalDiskBlobStore` (`System.IO` against the Synology NAS mount, configured via `BlobStorage:RootPath`) and `S3BlobStore` (`AWSSDK.S3`, configured via `BlobStorage:S3:ServiceUrl`, `ForcePathStyle`, and `BucketName`). Leaving `ServiceUrl` blank targets real Amazon S3 via the default AWS credential chain (IAM role / env / profile) and `BlobStorage:S3:Region`; setting it points `AmazonS3Client` at any S3-compatible endpoint - notably the `floci` emulator in the PR preview stack (ADR 19) - authenticated with `BlobStorage:S3:AccessKey`/`SecretKey`. The third-party `FluentStorage` package has been removed.
* **Rationale:** FluentStorage is unmaintained. An app-owned interface is the genuinely cloud-agnostic pattern: Azure Blob / S3 / GCS adapters can be added later behind DI without changing application code. `S3BlobStore` is verified in CI against the real S3 API surface (bucket create, put/get/delete) via `Testcontainers.Floci`, rather than mocking the AWS SDK.

## ADR 04: Microsoft Garnet for In-Memory Caching
* **Decision:** Deploy Microsoft Garnet instead of standard Redis.
* **Rationale:** Multi-threaded .NET backend, high performance, and RESP protocol compatibility.

## ADR 05: Layer 7 High Availability via Kemp LoadMaster
* **Decision:** Deploy dual Blazor Web LXCs across two separate Proxmox nodes behind a Kemp LoadMaster Virtual Service VIP (`10.10.110.199`, VLAN 110 — see ADR 23 for why this differs from the WUI's `10.10.10.199`).
* **Rationale:** Zero-Downtime Maintenance and active health checking.

## ADR 06: UniFi Network Segregation (VLANs)
* **Decision:** Segregate the architecture into three isolated VLANs (110, 120, 130) managed by the UniFi gateway.
* **Rationale:** Prevents unauthorized lateral movement.

## ADR 07: Message Brokering Abstraction via Wolverine
* **Decision:** Use Wolverine for all asynchronous messaging and background processing, backed by RabbitMQ in the home lab. MassTransit has been removed. `Messaging:Transport` (`rabbitmq` | `sqs` | `servicebus`, default `rabbitmq`) selects the broker purely via configuration, wired through `MessagingTransportConfigurator` (`WolverineFx.RabbitMQ` / `WolverineFx.AmazonSqs` / `WolverineFx.AzureServiceBus`) in `Program.cs` section 6. Independent of transport choice, `MessagingTransportConfigurator.ConfigureDurability` wires a Postgres-backed durable outbox/inbox (`WolverineFx.Postgresql`'s `PersistMessagesWithPostgresql(dbConnectionString, "wolverine")` + `Policies.UseDurableOutboxOnAllSendingEndpoints()`/`UseDurableInboxOnAllListeners()`): every message is persisted in the same Postgres instance before it touches the broker, so a broker outage delays delivery rather than losing the message. The envelope is written in Wolverine's own transaction, *not* enlisted in a caller's EF Core transaction — making a send atomic with a business change would additionally require `WolverineFx.EntityFrameworkCore` + `UseEntityFrameworkCoreTransactions()`, which nothing needs yet.
* **Rationale:** MassTransit v9 went commercial. Wolverine provides the same transport-agnostic, `IBus`-style abstraction (`IMessageBus`) while remaining free/open-source and lighter weight — handlers (`ProcessBidHandler`) are plain static classes discovered automatically and never change when the transport changes, proving the abstraction is real rather than aspirational. If the application migrates to Azure or AWS, the transport swap is one config value; the SQS/Service Bus code paths are exercised against the Floci emulator in local dev and the PR preview stack rather than only against real cloud accounts. The durable outbox is what makes "kill the broker, publish, restart the broker, watch it flush" a real demo rather than a claim: Postgres is already a hard dependency of the app, so this is one config block, not new infrastructure. Wolverine's own envelope-storage schema (`wolverine.*`, distinct from the app's EF Core schema) is auto-applied on startup only in `Development` (`UseResourceSetupOnStartup()`) for local/Aspire convenience; production applies it as a deliberate one-time step for the same reason ADR 11 forbids `Database.Migrate()` on boot — two HA nodes must never race on schema creation. That step is the **Apply Wolverine Envelope Schema** stage in `deploy-blazor.yml`, which runs `dotnet BrewHouse.dll db-apply` immediately after the EF Core migration bundle and before any node is deployed. The CLI exists because `Program.cs` ends in `RunJasperFxCommands(args)` rather than `app.Run()`; with no arguments that starts the web host identically, so the systemd unit is unaffected.

## ADR 08: SignalR WebSockets Scale-Out via Microsoft Garnet Backplane & Kemp Sticky Sessions
* **Decision:** Configure Blazor Server SignalR hubs to use Microsoft Garnet as a distributed pub/sub backplane (`AddStackExchangeRedis`), while enforcing L7 Session Persistence (Sticky Sessions) on the Kemp LoadMaster. `BidsHub` (`Hubs/BidsHub.cs`) is a broadcast-only hub on the same backplane: `ProcessBidHandler` pushes `BidPlaced` to `Clients.All` after saving a bid, and every Blazor circuit's `LiveBids.razor` component (via `IBidsClient`/`SignalRBidsClient`) re-renders on receipt - proving the cross-node broadcast rather than just documenting it as possible.
* **Rationale:** Blazor Server holds circuit state in application RAM. Sticky Sessions ensure a user's persistent WebSocket connection remains anchored to their assigned Blazor LXC node. If a cross-node broadcast occurs (e.g., live auction bid update), Garnet synchronizes the SignalR hubs across `Web 01` and `Web 02` instantaneously. `IBidsClient` is an app-owned abstraction over the concrete `HubConnection` so `LiveBids.razor` is unit-testable with bUnit without a real Kestrel/hub endpoint. Confirmed live: this Kemp license (Free/Trial VLM) exposes only `None`/`Source IP Address` persistence in the GUI — cookie-based `Super HTTP` persistence is not available — so the actual persistence mechanism is Source IP, not a cookie, despite "L7" in this ADR's title.

## ADR 09: Full Observability via OpenTelemetry (OTLP)
* **Decision:** Emit logs, metrics, and traces from the application via OpenTelemetry, exported over OTLP (`UseOtlpExporter` driven by `OTEL_EXPORTER_OTLP_ENDPOINT`). Serilog and `Serilog.Sinks.Grafana.Loki` have been removed.
* **Rationale:** Three signals instead of logs alone, using a vendor-neutral wire protocol. Locally the OTLP endpoint is the Aspire Dashboard; in production it is Grafana Alloy on VLAN 130, which fans out to Loki/Tempo/Prometheus. Blazor Server apps spread across multiple LXC nodes (`Web 01`, `Web 02`) make SSH/`journalctl` debugging unscalable.

## ADR 10: Deep Health Checks for Kemp L7
* **Decision:** Expose `/health` using `Microsoft.Extensions.Diagnostics.HealthChecks` to verify Postgres, Garnet, and RabbitMQ connectivity.
* **Rationale:** Prevents Kemp from routing traffic to a Blazor LXC that has lost backend connectivity, enabling true zero-downtime failover.

## ADR 11: EF Core Migration Bundles in CI/CD
* **Decision:** Generate and execute standalone EF Core Migration Bundles during the GitHub Actions deployment pipeline, instead of running `context.Database.Migrate()` on application boot.
* **Rationale:** Prevents database lock contention and schema race conditions when both HA nodes start simultaneously.

## ADR 12: Secrets Delivery via Infisical Agent & systemd EnvironmentFile
* **Decision:** The Infisical Agent, running on **each web LXC itself** (VLAN 110 — the Infisical *server* is the one on VLAN 130, ADR 26; the Agent is a separate small process co-located with the app it's feeding), renders `/etc/brewhouse/brewhouse.env`, which systemd loads via `EnvironmentFile=`. The `Infisical.Sdk` package has been removed from application code; the app fails fast with a descriptive error if connection strings are missing. The Agent's install/config (an `infisical-agent` Ansible role, ADR 28) uses a **read-only** machine identity, distinct from the write-scoped one `infisical-secret` uses — the credential that ends up deployed onto two internet-facing-adjacent LXCs should never also be able to overwrite secrets.
* **Rationale:** No SDK or authentication code lives inside the app, and the pattern works identically for any process type (not just .NET). Secrets still never appear in `appsettings.json` and remain secured within the isolated VLAN 130 Infisical vault.

## ADR 13: Let's Encrypt Wildcard Certificates via DNS-01 & Kemp LoadMaster
* **Decision:** Utilize the native Let's Encrypt ACMEv2 client built into the Kemp LoadMaster to automatically request and renew wildcard certificates (`*.smartsoftwarecoffee.com`) using the DNS-01 challenge against the Cloudflare API. `Blazor-App-VIP` (`10.10.110.199:443`) is built as a Content-Switching parent with a single SubVS holding the real servers, not a VS with Real Servers attached directly — confirmed live, Kemp's ACME wizard only lists SubVS-based VSs as valid certificate targets (`docs/09` section 1). The certificate must then be manually assigned to the VS after issuance (`docs/09` section 3) — Kemp does not bind it automatically.
* **Rationale:** The DNS-01 challenge allows for the issuance of trusted certificates for internal, non-publicly routable networks without opening firewall ports. By terminating SSL at the Kemp LoadMaster, all Blazor backend LXCs are offloaded from certificate management, avoiding "Not Secure" browser warnings for internal admin endpoints.

## ADR 14: Local Orchestration via .NET Aspire AppHost
* **Decision:** Use a .NET Aspire AppHost (`src/BrewHouse.AppHost`) for local development orchestration, replacing `docker-compose.local.yml` (deleted).
* **Rationale:** Aspire provisions the PostgreSQL (pgvector), Garnet, and RabbitMQ containers with data volumes and injects connection strings into the app dynamically as `ConnectionStrings__brewhousedb` / `__cache` / `__messaging` — no static local configuration to drift. Integration tests reuse the exact same dependency graph via `Aspire.Hosting.Testing`, guaranteeing local dev and CI test against identical infrastructure.

## ADR 15: HAProxy + Keepalived as the Documented Load-Balancer Alternative
* **Decision:** Document HAProxy + Keepalived as the free, open-source alternative to the Kemp LoadMaster (ADR 05): HAProxy stick tables provide Blazor Server session persistence, and Keepalived (VRRP) provides load-balancer redundancy.
* **Rationale:** Kemp remains the current choice, but if licensing becomes an issue, HAProxy + Keepalived delivers equivalent L7 health checking, sticky sessions, and VIP failover at zero license cost.

## ADR 16: Rollback via Symlinked Releases, Pre-Migration pg_dump & Guarded Automated DB Restore
* **Decision:** Deploys publish into `/var/www/brewhouse/releases/<git-sha>` and atomically flip a `current` symlink (last 5 releases retained per node). The manual `rollback.yml` workflow re-points the symlink and restarts, health-gated per node. Before every EF migration bundle execution, CI takes a `pg_dump` of the database to the Synology NAS. Database restore is **automated in the same workflow** behind two human gates: `production` environment approval and a typed `RESTORE` confirmation. The restore is non-destructive — the dump is loaded into a fresh database, sanity-checked, and the databases are RENAME-swapped; the previous database is preserved as `brewhouse_db_failed_<timestamp>` and dropped only by explicit manual action after verification.
* **Rationale:** In-place `rsync --delete` deploys made the previous version unrecoverable, and forward-only migrations had no safety net. Symlink flips make app rollback a seconds-long operation; the pre-migration dump bounds database data loss to writes made after the deploy began. Automating the restore removes error-prone manual SSH during an incident, while the approval + typed-confirmation gates satisfy the RED RULE that destructive database operations never run unattended.

## ADR 17: Infrastructure as Code via Terraform (bpg/proxmox + resnickio/unifi) & Ansible
* **Decision:** All LXCs, UniFi VLANs, and firewall policies are declared in `terraform/` (`bpg/proxmox` for Proxmox VE, `resnickio/unifi` for the UDM-Pro). LXC configuration — .NET runtime, NFS mounts, systemd units, pgBackRest — is converged by `ansible/` over SSH. Terraform renders the Ansible inventory on every apply, so the pipeline is `terraform apply && ansible-playbook site.yml`. systemd unit files are copied by Ansible verbatim from `src/systemd/` (one canonical copy). The Kemp LoadMaster remains GUI-managed (no supported provider).
* **Rationale:** Manual `pct` / community-script provisioning and hand-built firewall rules were the last unreproducible part of the lab and could not be reviewed in a PR. Declarative IaC makes the whole environment reproducible, idempotent, and diff-able; keeping the LXC matrix (`lxc.tf`) as a code mirror of the `docs/04` matrix enforces the docs-as-source-of-truth workflow. `resnickio/unifi` (not the more common `paultyng/unifi`) is required because the real controller runs UniFi Network 10.6.101: that version's zone-based firewall rejects every write from `paultyng/unifi`'s `unifi_firewall_rule` resource (legacy `LAN_IN`/`rule_index` model, `api.err.FirewallRuleIndexOutOfRange` on every attempt — a known, unresolved limitation of that provider on UniFi 8.x+). `resnickio/unifi`'s `unifi_firewall_policy` resource targets the new zone-based API instead. `bpg/proxmox` authenticates as `root@pam` via password (`providers.tf`), not the scoped API token the docs originally called for — confirmed live that Proxmox hardcodes several container operations to `root@pam`-only regardless of an API token's assigned role: creating a privileged container, setting any `features` flag but `nesting`, and a bind-type `mount_point`. `blazor-web-01/02` and `postgresql` need all three — unprivileged LXCs can't mount NFS in-guest at all (feature flag or not), and a bind `mount_point` on an unprivileged container masks the mounted content's permissions to `0000`/`nobody:nogroup` inside the guest (a kernel user-namespace safety behavior), so those three are privileged and bind-mount the NAS share from the Proxmox host (`docs/04`). The provider's own docs confirm auth is all-or-nothing (an `api_token`, if set, takes precedence over `username`/`password`) — so `root@pam` is the credential for every Terraform-managed Proxmox resource, not a scoped exception for just those three.

## ADR 18: pgBackRest Continuous WAL Archiving for PITR
* **Decision:** The PostgreSQL LXC runs pgBackRest (configured by `ansible/roles/postgres`) with `archive_command` pushing WAL to a repo on the Synology NAS (`/mnt/synology/postgres-data/pgbackrest`, `archive_timeout=60s`), plus scheduled full (weekly) and differential (nightly) backups via systemd timers (`repo1-retention-full=2`, `repo1-retention-diff=7`). Point-in-time recovery (`pgbackrest --delta --type=time restore`) is documented in `docs/10` section 4. The pre-migration `pg_dump` and its prune timer are retained as a logical, schema-level belt-and-braces copy.
* **Rationale:** The ADR 16 `pg_dump` restore path loses every write between the dump and the restore — unacceptable for an auction workload with live bids. Continuous WAL archiving bounds data loss to at most ~60 seconds of in-flight transactions, effectively eliminating the rollback data-loss window, while pgBackRest's retention/expire handles repo pruning automatically.

## ADR 19: Ephemeral PR Preview Environments on a Single Non-Prod Docker Host
* **Decision:** Every open PR gets an isolated preview environment on a dedicated non-prod LXC (`pr-preview`, VLAN 140, `10.10.140.120`) that runs **Docker** — one compose stack per PR (`deploy/preview/docker-compose.pr.yml`: app + pgvector Postgres + Garnet + RabbitMQ + the four Floci multi-cloud emulators (AWS/Azure/GCP/OCI, ephemeral/memory-mode/no Docker socket), project `pr-<n>`). The `pr-preview.yml` workflow (self-hosted runner, `preview` environment) builds the image, ships it to the host, runs the EF Core migration bundle against the per-PR database, registers a Caddy site (app + one per emulator), and comments the URL on the PR. `pr-preview-cleanup.yml` (`pull_request: closed`) tears the stack down with `docker compose down -v` and removes the (single, multi-block) Caddy site file. Caddy terminates TLS on 443 and reverse-proxies to each stack's loopback-only ports (`6000 + <PR#>` app, `24566/24577/24588/24599 + <PR#>` emulators). VLAN 140 is firewalled off from the production tiers (`terraform/unifi.tf`). This deliberately relaxes ADR 02 for non-prod only — production remains Docker-free on systemd LXCs. Separately, Ansible's `preview-host` role deploys a **standing**, persistent-storage Floci stack (`/opt/floci/`, `../floci/README.md` section 4 verbatim, Docker socket mounted) independent of any PR — the per-PR services deliberately do **not** get socket access, since that would hand an untrusted PR branch a path to the host Docker daemon.
* **Rationale:** Testing against real backing services before merge catches integration bugs that bUnit/handler tests cannot. Docker compose gives perfect per-PR isolation and one-command cleanup (`down -v` removes containers, networks, and the PR database volume) — something native systemd instances with shared Postgres/RabbitMQ cannot match without bespoke teardown logic. A single preview host keeps non-prod cost and sprawl minimal; the Kemp/sticky-session HA layer is prod-only and intentionally not replicated. Floci lets `S3BlobStore` (ADR 03) and the SQS Wolverine transport (ADR 07) be exercised against a real cloud API surface per PR without an AWS/Azure account — the preview app is wired to it by default (`BlobStorage__Provider=s3` against `http://floci:4566`, with a one-shot `floci-init` container creating the per-PR bucket, since `S3BlobStore` deliberately never creates buckets itself); the SQS transport is a two-line env override documented in `docs/11`; the standing stack exists for ad-hoc/demo use and the container-driving features (Lambda, RDS, ECS, Cloud Run) that a per-PR, socket-free stack cannot offer.

## ADR 20: Internal DNS (Technitium Wildcard) & Internal PKI (step-ca ACME) for Non-Prod
* **Decision:** A Technitium DNS LXC (VLAN 130, `10.10.130.119`) serves the private zone `pr.brewhouse.internal` with **one wildcard A record** `*.pr.brewhouse.internal → 10.10.140.120`, so every PR preview is resolvable with zero per-PR DNS churn — nothing to create or clean up on merge. A step-ca LXC (VLAN 130, `10.10.130.121:4443`) acts as the internal certificate authority with an **ACME provisioner**; Caddy on the preview host issues per-PR and ops-stack certificates automatically via a **per-site `tls { ca ...; ca_root ... }` block** (see ADR 25 — not a global `acme_ca` directive), validating TLS-ALPN-01 challenges over the LAN. Clients trust the step-ca root certificate once (GPO/manual install). The zone uses the ICANN-reserved `.internal` TLD — guaranteed never to collide publicly or leak. Production TLS is unchanged: Let's Encrypt DNS-01 wildcard on the Kemp (ADR 13).
* **Rationale:** PR environments must never be publicly exposed, so public CAs and DNS-01 against Cloudflare are the wrong tool for non-prod. A wildcard DNS record eliminates an entire class of CI DNS bookkeeping (and its failure modes on merge). step-ca's ACME provisioner lets stock Caddy automate issuance/renewal with no plugins, and a locally-trusted root CA gives the same "green padlock" experience internally that ADR 13 delivers for production.

## ADR 21: Fleet-Wide Cockpit & Containerized Admin Tooling Behind Internal DNS Names
* **Decision:** Every LXC runs **Cockpit** (`:9090`) with a TLS certificate signed by the internal step-ca — issued centrally on the CA host via the JWK provisioner and distributed by Ansible (`/etc/cockpit/ws-certs.d/`), so every admin console is a green padlock for clients that trust the internal root. The preview host additionally runs an always-on **ops compose stack** (`/opt/ops/`, separate from the per-PR stacks): **Portainer** (container management), **Dozzle** (log viewer), **Watchtower** (nightly image updates, restricted to labeled ops containers — running PR stacks are never mutated), **pgAdmin 4**, and **RedisInsight**. All UIs are loopback-only behind Caddy on 443 with step-ca-issued certificates. Technitium serves a second private zone **`brewhouse.internal`**: one A record per LXC plus friendly CNAMEs (`portainer.`, `dozzle.`, `pgadmin.`, `redisinsight.`) — nothing public-facing gets a record. Two targeted firewall exceptions let the preview host's pgAdmin/RedisInsight reach production PostgreSQL (`5432`) and Garnet (`6379`); all other VLAN 140 → production traffic stays dropped.
* **Rationale:** Admin tooling deserves the same internal-PKI/DNS treatment as the app tiers — no port memorization, no certificate warnings, no public exposure. Running the admin UIs on the non-prod Docker host keeps production LXCs minimal (ADR 02) while giving operators GUI access to both environments from one place; the two port-scoped firewall exceptions are the smallest possible relaxation and are code-reviewed in `terraform/unifi.tf`. Centralized cert issuance on the CA host avoids opening ACME challenge paths into every VLAN.

## ADR 22: GitOps-Driven Infrastructure Changes via a Manual DevOps LXC
* **Decision:** Terraform and Ansible no longer run from an operator's workstation. A single, manually-provisioned (not Terraform-managed) Debian 12 LXC on `pve1` — outside the fleet Terraform can destroy — hosts the GitHub Actions self-hosted runner, Terraform, Ansible, and the SSH key Ansible uses against every managed LXC. Two workflows drive infrastructure changes the same way `deploy-blazor.yml`/`rollback.yml` drive app changes: `terraform-plan.yml` runs `terraform plan` on every PR touching `terraform/**` and posts the plan as a PR comment; `terraform-apply.yml` is `workflow_dispatch`-only, gated by the `production` environment's required reviewer, and applies the *exact* plan artifact a human already reviewed on the PR — never a freshly regenerated plan — before running `ansible-playbook site.yml` to converge the result. Sensitive inputs (`proxmox_password`, `unifi_password`) are GitHub Actions secrets injected as `TF_VAR_*` environment variables at runtime; non-sensitive inputs are repository variables. No `terraform.tfvars` file is required for the CI path.
* **Rationale:** Every other production change in this repo goes through a reviewed PR and an approval gate (ADR 11's migration bundle, ADR 16's rollback workflow) — infrastructure was the one exception, since `terraform apply` was always a human running a local command, unreviewed and unaudited. Running it via CI closes that gap. The control box must live outside Terraform's own blast radius (`pve1`, alongside Kemp — see `docs/04`) specifically because it is the thing capable of destroying the fleet: co-locating it with a Terraform-managed LXC risks a bad apply severing the SSH session running that very apply. Applying the saved plan artifact rather than a fresh one at apply time mirrors the EF Core migration bundle's "build once, execute exactly that artifact" discipline (ADR 11) — a plan reviewed on Monday and a plan silently regenerated on Friday are not the same guarantee.

## ADR 23: Kemp Dual-NIC Segmentation — WUI on the Existing LAN, VIP on VLAN 110
* **Decision:** The Kemp LoadMaster VM (`VMID 199` on `pve1`) runs two NICs: `eth0` stays on the existing LAN (`10.10.10.0/24`, untagged), carrying only the WUI at `10.10.10.199`; `eth1` is tagged into VLAN 110 (`qm set 199 -net1 ...,tag=110`, applied outside Terraform since Kemp itself isn't Terraform-managed), carrying the Virtual Service VIP at `10.10.110.199`, alongside the Blazor real servers and the Cloudflare Tunnel LXC it serves.
* **Rationale:** Confirmed live: Kemp refuses to let a Virtual Service reuse the IP address of *any* of its own interfaces ("Cannot use WUI address as a VIP") — the rule applies per-interface, not just to eth0. The original single-NIC design collided the WUI and the VIP on the same address; splitting onto a second NIC preserves `.199` as the memorable address on *both* segments (the VM's own Proxmox VMID) while eliminating the collision, and additionally moves ingress traffic onto the same VLAN as the real servers and the Cloudflare Tunnel LXC it targets, removing a cross-VLAN hop that existed in the original single-subnet design.

## ADR 24: HTTP → HTTPS Redirect Handled at the Application Layer, Not Kemp
* **Decision:** The Blazor app's port-80 traffic is not redirected by Kemp. Both the `10.10.110.199:80` and `:443` Virtual Services forward to the same real servers (`10.10.110.101/102:5000`, plain HTTP — TLS never reaches them); `src/BrewHouse/Program.cs` calls `UseForwardedHeaders` (trusting `X-Forwarded-Proto`/`X-Forwarded-For` only from Kemp's `eth1` address, `10.10.110.198`) followed by `UseHttpsRedirection()`, so the app itself issues the 301 based on which VIP port the client actually hit.
* **Rationale:** Confirmed live: this Kemp license exposes no built-in "force HTTPS"/redirect toggle on the Virtual Service (Standard/Advanced Properties have no such field; it may require the licensed ESP add-on), and Advanced Properties itself stays sparser on a VS until a certificate is bound and SSL Acceleration is active. Rather than depend on an unverified/possibly-unlicensed Kemp feature, `UseForwardedHeaders`/`UseHttpsRedirection` is the standard ASP.NET Core pattern for exactly this reverse-proxy scenario, is portable to ADR 15's HAProxy alternative without any app change, and only requires Kemp to attach one standard header on the `:443` VS.

## ADR 25: Per-Site `tls` Blocks Required for Caddy to Use step-ca on `.internal` Names
* **Decision:** Every Caddy site for a `.internal` hostname — the ops-stack sites (`ops.caddy.j2`), the Floci console (`floci.caddy.j2`), and every per-PR site CI writes (`pr-preview.yml`) — declares its own `tls { ca {{ step_ca_url }}/acme/acme/directory; ca_root /etc/caddy/pki/root_ca.crt }` block. `Caddyfile.j2`'s global block deliberately does **not** set `acme_ca`/`acme_ca_root` — that directive is now absent there entirely.
* **Rationale:** Confirmed live, and it cost real debugging time: Caddy's automatic HTTPS treats any hostname ending in `.internal` (also `.local`, `.localhost`, single-label names) as ineligible for a publicly-issued certificate, and for such names it silently substitutes its own self-signed "Caddy Local Authority" issuer — **even with a global `acme_ca` configured**, because that global directive only supplies the issuer for hostnames that already pass the public-eligibility check. Adding an *identical* `tls { ca ...; ca_root ... }` block to every site did not fix this on its own: `caddy adapt` showed the global directive and the per-site blocks being merged into one subject-less automation policy, which Caddy's internal-CA override doesn't recognize as "this domain already has its own policy," so the override fired anyway. Only removing the global directive — so each site's `tls` block is the sole source of that policy — makes `caddy adapt` emit a `subjects`-scoped policy per hostname, which the override then correctly skips. Separately confirmed live: a `systemctl reload caddy` (soft config reload) does not drop already-cached in-memory certificates even after the on-disk cert files for a domain are deleted — only a full `systemctl restart caddy` forces Caddy to re-evaluate storage and actually re-issue.

## ADR 26: Infisical Self-Hosted via the Official Bare-Metal Package, Not Docker
* **Decision:** The `infisical` LXC (`10.10.130.116`, VLAN 130) runs Infisical's own `infisical-core` Debian package (an Omnibus-style installer, like GitLab's — configured via `/etc/infisical/infisical.rb` and applied with `infisical-ctl reconfigure`), backed by a **local** PostgreSQL + Redis on the same LXC — not the shared brewhouse Postgres. The Ansible `infisical` role installs and configures all of this; previously Terraform only created the bare LXC shell and nothing installed the application itself. The exact package/repo/config sequence was sourced from the community-scripts ProxmoxVE installer (`ct/infisical.sh` / `install/infisical-install.sh`, commit `787dbf2420ec8217c967eb4c152cb3003446d327`) rather than guessed. Infisical listens on **port 8080**, not 80.
* **Rationale:** This was a genuine gap, not a config error — nothing in the repo (Terraform or Ansible) ever installed the Infisical server, only the client-side Agent role that runs on the Blazor web LXCs. Infisical's own self-hosting docs lead with Docker Compose, which would need an ADR 02 exception; the community-scripts installer proved a fully bare-metal path exists and is officially packaged, so no exception is needed. A dedicated local database (rather than a schema on the shared brewhouse Postgres) keeps the vault reachable even while that database is down or mid-migration — exactly the failure mode a secrets store must survive.

## ADR 28: Ansible Pushes Secrets Into Infisical Directly, Instead of Manual Copy-Paste
* **Decision:** A reusable `infisical-secret` role (`include_role`'d with `infisical_secret_name`/`infisical_secret_value` set) authenticates to Infisical's API as a **second, write-scoped machine identity** — separate from the read-only one the Agent uses on the web LXCs (`docs/07`/ADR 12) — and does a confirmed-live POST-then-PATCH (create, and on `400`/"already exists" fall back to update; there is no single upsert endpoint). The `garnet`, `rabbitmq`, and `observability` roles each call it as their last task, pushing `ConnectionStrings__cache`, `ConnectionStrings__messaging`, and `OTEL_EXPORTER_OTLP_ENDPOINT` respectively the moment each service is actually provisioned. `site.yml` runs the `infisical` play **first** so it's already up before anything tries to push into it. The two Infisical-side identifiers this all depends on (`infisical_project_id`, `infisical_environment`) plus the write identity's own Client ID/Secret live in `ansible/inventory/group_vars/all/secrets.yml` (git-ignored, split from `all/vars.yml` — same "Ansible, supplied by you" pattern as Technitium's API token) — every one of these four values is itself generated by Infisical and does **not** survive a teardown/rebuild of the `infisical` LXC, so this file has to be re-populated once per Infisical-instance lifetime, same as re-trusting the step-ca root after a rebuild. `ConnectionStrings__brewhousedb` is the one exception: Postgres role/database creation is still a manual shell block (`LAB-RUNBOOK.md` step 1.2), not an Ansible role, so its push is a `curl` call appended to that same block rather than a fourth Ansible role wired to `infisical-secret`.
* **Rationale:** The user asked directly whether secrets could be pushed programmatically as each service is provisioned, rather than hand-copied into Infisical's UI — reasonable, since that hand-copy step was the thing actually blocking progress (two of four keys had no real value to copy at all until ADR 27 filled the Garnet/RabbitMQ gap). A second write-scoped identity, rather than upgrading the Agent's own identity, keeps every already-deployed web LXC holding only read access — the blast radius of that credential leaking stays "can read secrets," never "can also overwrite them." Landing this in each service's own role (not a separate end-of-run play) means "provisioned" and "secret is in Infisical" happen atomically — there's no window where Garnet is up but Infisical doesn't know its connection string yet.

## ADR 32: First-Ever Approved Deploy Surfaced Two Real, Pre-Existing CI Bugs
* **Decision:** `deploy-blazor.yml`'s `Restore & Test` step gates every deploy on the full test suite, including an Aspire-orchestrated integration test that starts the whole local app graph (Postgres, Garnet, RabbitMQ) via DCP. The first time any deploy run ever got past the `production` environment's required-reviewer gate (this session), it failed — a gap nobody had hit before because nothing had ever been approved. (2) **Aspire's `AddRedis()` resource type injects its own `redis-server` startup command regardless of which image is substituted in** — Garnet's image only has `/app/GarnetServer`, so the container crashed with exit code 127 ("redis-server: not found") every single time, invisibly, because DCP's own resource-creation timeout (a fixed internal window, independent of any test-level Polly timeout) always expired first with a generic `TaskCanceledException` that named neither bug. `.WithEntrypoint("/app/GarnetServer")` fixes it.
* **Rationale:** Both bugs were undiagnosable from the CI failure message alone (`Polly.Timeout.TimeoutRejectedException`, no mention of Garnet, GHCR, or exit codes anywhere) — confirmed only by running the AppHost directly on the runner outside the test harness and reading DCP's own debug-level logs (`Logging__LogLevel__Aspire=Debug`), then binary-searching resource-by-resource with `docker ps -a` to find which one never even got a container. Neither bug is specific to production (the real Garnet LXC deployment from ADR 27 is unaffected — separate binary, separate systemd unit, no Aspire/DCP involved at all) — this only affects the local-dev/CI-testing AppHost path (ADR 14).

## ADR 29: Infisical Agent Install Moved Into Ansible, Surfaced a Firewall-Ordering Bug
* **Decision:** A new `infisical-agent` role, added to the `web` play, replaces what was a fully manual per-LXC block in `LAB-RUNBOOK.md` step 8 (install the CLI package, hand-write `client-id`/`client-secret`/`agent-config.yaml`, install a systemd unit). Getting it working live surfaced two real bugs, both now fixed at the source rather than worked around: (1) these minimal LXC images have no `curl` — `curl ... | bash` was silently "succeeding" doing nothing, because a pipeline's exit status is its *last* command's (`bash`, which exits 0 on empty stdin), not `curl`'s; the role now installs `curl` first. (2) `terraform/unifi.tf` never had a rule allowing VLAN 110 (web) to reach the Infisical LXC on `8080` at all — added one, but a first attempt still failed: `unifi_firewall_policy`'s `index` field is controller-assigned and **read-only** (confirmed via the provider's own schema), so the new allow rule was simply appended after the pre-existing `drop_web_to_mgmt` rule regardless of Terraform's `depends_on` (which only orders API calls during apply, and doesn't touch the index of a resource that isn't itself being changed). Fixed with `terraform apply -replace=unifi_firewall_policy.drop_web_to_mgmt`, forcing it to be destroyed and recreated so the controller assigns it a fresh, later index.
* **Rationale:** Same reasoning as ADR 26/27 — `ansible-playbook site.yml` should finish with the app *actually able to start*, not "mostly done, now SSH in three more times by hand." Both bugs were things no amount of re-reading the Ansible/Terraform code would have caught — the curl gotcha only shows up as a pipeline that reports success while doing nothing, and the firewall-ordering gotcha only shows up as a connection that still times out after the "fix" is already applied. Worth documenting `docs/05`'s firewall table with the `index`-ordering caveat specifically, since any *future* allow rule added against an already-existing drop rule on the same source/destination pair will hit the identical bug.

## ADR 35: Generated Credentials and Fetched Artifacts Moved to Absolute Paths Outside Any Git Checkout
* **Decision:** Every `lookup('ansible.builtin.password', ...)` call (step-ca, pgAdmin, RabbitMQ, Postgres/brewhouse, Infisical, PatchMon, Technitium's bootstrap password) now caches under `/opt/ansible-credentials/...` instead of the previous repo-relative `credentials/...`. Every `ansible.builtin.fetch` destination and its downstream consumers (the step-ca role's `root_ca.crt` and per-host Cockpit certs; the `preview-host`/`cockpit` roles that install them) similarly moved from a relative `fetched/...` (or `{{ playbook_dir }}/fetched/...`) to `/opt/ansible-fetched/...`. Both directories are created once on the devops LXC (section 0 step 9).
* **Rationale:** Confirmed live, and it caused a real outage: this LXC has **two** separate clones of the infra repo — the manual one used for interactive work, and the GitHub Actions self-hosted runner's own `_work` checkout used by `ansible-converge.yml`/`terraform-apply.yml`. A relative path — for a generated credential *or* a fetched artifact — resolves independently in each clone, with no way for the two to ever agree. For generated credentials this silently broke Infisical: its Postgres role's password diverged between clones (crash-looping on `password authentication failed`), and separately its `ENCRYPTION_KEY` diverged too — far more serious, since that key decrypts the KMS root key protecting every secret already stored in the database (`InternalServerError: the configured encryption key does not decrypt this database's root key`). Recovered by identifying which clone's cached value was the one actually in use when the data was first written (the manual clone, confirmed by testing against the live error message) and aligning the live Postgres role and `infisical.rb` to it via `infisical-ctl reconfigure` (a plain `restart` does not reload the underlying env file — confirmed live). The identical divergence then surfaced for fetched artifacts the moment a full playbook run was attempted from the runner's own clone: `preview-host`/`cockpit` failed outright looking for `root_ca.crt`/per-host certs that had only ever been fetched into the *other* clone's directory. Absolute, shared paths remove the entire failure class going forward, for every current and future generated credential or fetched artifact, not just the ones that broke this time.

## ADR 36: "Supplied by You" Secrets Moved to `/opt/ansible-secrets`, Passed as `-e @file`
* **Decision:** The `secrets.yml` files documented in "Handling secrets" bucket 3 (Technitium's API token, Infisical's project ID and both machine identities) no longer live inside any git checkout at all — not even as a git-ignored file. * **Rationale:** Confirmed live, repeatedly: the previous approach (a per-group `secrets.yml` inside `ansible/inventory/group_vars/<group>/`, git-ignored) worked fine for manual use but broke CI runs on this LXC's GitHub Actions runner clone three separate times in one session — something in the runner's own checkout process kept silently removing the git-ignored file between jobs, even with `actions/checkout`'s `clean: false` set (the specific mechanism was never fully identified; `clean: false` alone did not prevent it). Each recurrence produced the same undefined-variable failure in `infisical-agent`'s "Write the Agent's client-id" task. Re-copying the file into the runner's checkout after each occurrence was not a fix, just a repeated workaround for the same unresolved cause. Moving the file itself outside any checkout removes the dependency on checkout behavior entirely, the same way ADR 35 did for generated credentials and fetched artifacts — this is that same fix applied to the one remaining category of file still living inside a checkout.

## ADR 39: PatchMon Agent Install Hung on `read -r response` Under Ansible's Allocated PTY

## ADR 40: Home Network Outage After Firewall Applies — UniFi Restored, Firewall Scope Narrowed, PatchMon Reachability Fixed Fleet-Wide
* **Decision:** After a home-network-wide outage (every Windows device, wired and wireless, stuck on `169.254.x.x` APIPA addresses) forced a restore of the UniFi controller from a 2-week-old backup, three things changed: (1) removed `pve1_to_nas`/`pve2_to_nas`/`pve3_to_nas`/`pve4_to_nas`/`mgmt_to_nas`/`data_to_nas_nfs`/`data_to_nas_nfs_portmapper` from `terraform/unifi.tf` entirely — none had a current consumer, confirmed live (see rationale); (2) added `preview_to_patchmon` (VLAN 140 → `10.10.130.122:3000`) and added it to `drop_preview_to_mgmt`'s `depends_on`, mirroring `web_to_patchmon` (ADR 37) — PatchMon reachability is now explicit for every tier (VLAN 110 via the explicit rule, VLAN 120 via the same-zone default-allow with no drop rule against it, VLAN 130 intra-zone, VLAN 140 via this new rule).
* **Rationale:** The outage was discovered days after `web_to_patchmon` and a `-replace` of `drop_web_to_mgmt` were applied (ADR 37) — both used the pattern of destroying and recreating the catch-all BLOCK policy to force it to re-evaluate after a new ALLOW, since `unifi_firewall_policy`'s `index` is controller-assigned and read-only. Disabling Terraform-created firewall rules from a still-connected Mac partially restored wired connectivity, which is real (if circumstantial) evidence the firewall policy set was at least implicated; a full UniFi backup restore was needed to fully resolve it, and Wi-Fi didn't recover until the next day. No `unifi_network` resource in this repo has DHCP enabled on any of the four managed VLANs, and none of them is the user's own LAN/Wi-Fi network, so there's no *direct* mechanism here for a VLAN config change to hand out APIPA addresses — if Terraform's changes were a cause at all, it would have to be the zone-based firewall policy compile/push destabilizing the gateway broadly enough to affect DHCP servicing platform-wide, not a targeted config change; the controller's own event log for that window wasn't recoverable (see below), so this can't be confirmed as definitive root cause, only as the most credible mechanism given what's known.
  The restore itself surfaced two further problems. First, the `terraform` UniFi service account's stored credentials stopped authenticating entirely (403 on every `terraform plan`) — the account was created or last had its password rotated more recently than the 2-week-old snapshot, so the restore rolled it back out of existence; the user recreated it by hand. Second, once auth was restored, `terraform plan` showed **28 to add, 0 to change, 1 to replace** — every single Terraform-managed `unifi_network` and `unifi_firewall_policy` resource, not just the two from ADR 37, meaning the restore wiped this repo's *entire* UniFi footprint back to whenever that snapshot was taken, not merely the most recent changes.
  With everything being recreated from scratch anyway, this was the moment to fix scope rather than reapply it as-is. The original "access denied by server" note that motivated adding these rules in the first place was almost certainly a NAS-side share-permission issue, not a firewall one. Deleted all four `pveN_to_nas` policies outright once confirmed, rather than leaving them commented out. Separately, investigating the earlier stuck-CI incident (ADR 39) had already found `pr-preview` fatally failing PatchMon enrollment because `drop_preview_to_mgmt` blocked it with no exception carved out — same class of gap as ADR 29/37, now closed the same way.
  Finally, added `terraform/unifi-backup.sh` and a step in `terraform-apply.yml` that runs it before `terraform init`'s apply — it logs into the UniFi OS Console's own API (`/api/auth/login`, extracting the `X-CSRF-Token` response header), triggers `POST .../cmd/backup`, and downloads the resulting `.unf` file to `/opt/unifi-backups/` (outside any git checkout, ADR 35 pattern) with a UTC timestamp. Confirmed live this session end-to-end (login, CSRF, backup command, and downloading a real ~18MB file) before wiring it in. The whole point of this ADR was "we didn't have a recent backup when we needed one" — this makes that structurally impossible for any future `terraform apply` in this repo, CI or manual. **Restore procedure, confirmed live separately (2026-09-19):** these files do **not** appear in the UniFi console's own Settings → Backups list (that list only tracks the controller's own `Auto (Weekly)`/`Back Up Now` snapshots — `cmd/backup` is a different, parallel mechanism) — restoring one means Settings → Backups → **Restore** → **Upload Backup File**, not picking from that dropdown. Worth remembering under pressure: the obvious-looking restore path in the UI won't show these backups at all.

## ADR 41: DNS + Certs for Physical/Appliance Infrastructure, UI Credentials Centralized in Infisical

## ADR 48: blazor-web-01/02 Bumped to 2GB RAM / 1GB Swap After a Live Wedge Incident
* **Decision:** `blazor-web-01` (VMID 401, `10.10.110.101`) went completely unresponsive in production (2026-09-18) — reachable by ICMP, but SSH accepted the TCP handshake and then never sent its banner, the app's `:5000` port never completed a handshake at all, and even `pct exec` into the container's namespace from its Proxmox host (`pve4`) timed out, so no diagnosis was possible while it was wedged. Proxmox itself still reported the container `status: running` throughout. A `pct reboot` issued from the host hung too (`lxc-stop` itself had to be interrupted); the container only actually came back once its physical host (`pve4`) was restarted directly. Immediately after boot, load average was 16–26 on a 2-core LXC, and the box wedged again within minutes. `blazor-web-01`/`blazor-web-02` (`terraform/lxc.tf`) are bumped from `memory = 1024` (no swap configured) to `memory = 2048, swap = 1024` — applied to both nodes for parity, not just the one that actually wedged.

The one memory snapshot actually captured, moments after the box came back, showed no pressure (132MB used, 891MB available, 0 swap used out of 1024MB total) — pointing more toward the observed severe load average (CPU contention from every systemd unit, the PatchMon agent, Cockpit, and the .NET JIT all racing for 2 cores at once during boot) than classic OOM. Bumping RAM/swap is a precaution against the plausible cause, not a confirmed fix — 1GB was already thin for Kestrel plus the fleet-wide Cockpit (ADR 21) and PatchMon (ADR 34) agents sharing the box, and 0 swap meant any transient GC/JIT spike had zero headroom before either the OOM killer or outright thrashing kicked in. This is exactly the gap the still-unbuilt fleet-wide patch playbook (`LAB-RUNBOOK.md` §5) needs to guard against going forward — a reboot loop against a wedged host is not a substitute for understanding why it wedged.

## ADR 49: Fleet-Wide Patching via a Manual-Only `patch-fleet.yml`, Web Tier Fully Offline During Patching
* **Decision:** A new `ansible/patch.yml` playbook and a `Patch Fleet` GitHub Actions workflow (`patch-fleet.yml`, `workflow_dispatch`-only — never a push or a schedule) close the "nothing re-patches an LXC after first stand-up" gap tracked in `LAB-RUNBOOK.md` §5. `ansible/patch.yml` is a single `hosts: all` play (the `--limit` passed at invocation decides scope): `apt update && apt upgrade -y`, `apt autoremove`, and an unconditional reboot (no `/var/run/reboot-required` check — a predictable reboot every run is simpler to reason about for an infrequent, manually triggered action) — plus, only for hosts in the `preview` group, `docker compose pull && up -d --remove-orphans` against the always-on ops stack (Portainer/Dozzle/Watchtower/pgAdmin/RedisInsight) after its reboot, forcing the same image refresh Watchtower already does nightly rather than waiting for its 4am schedule (per-PR preview stacks are never touched, same rule Watchtower itself follows). The workflow calls this playbook three times with different `--limit` values, bracketing only the `web` invocation with two new reusable GitHub Actions **composite actions** (`.github/actions/web-offline`, `.github/actions/web-online`): drop `app_offline.htm` (ADR 48's ASP.NET Core Module lookalike, `src/BrewHouse/Program.cs`) on **both** web nodes, patch+reboot both together via `--limit web`, then remove the file and gate on a real `/health` `200` from each before calling either node back — both nodes go down as a pair, not one-at-a-time behind Kemp, since there's no traffic-serving reason to keep the old code up while patches land. `/health` is deliberately **exempt** from the offline check (`src/BrewHouse/Program.cs`) — Kemp keeps polling it and keeps routing normally throughout, so real requests still land on a live Kestrel process serving the maintenance page. `deploy-blazor.yml` (app version upgrades, not OS patches) uses the **identical two composite actions**, replacing its old `curl .../health` gate (which would now legitimately 503 while the maintenance page is up) with a `systemctl is-active` check mid-deploy — and, a design-review correction before this ever ran live: `web-offline` runs **before** `Backup Database`/`Execute Migration Bundle`/`Apply Wolverine Envelope Schema`, not just before the rsync/restart steps. An earlier version of this workflow put the offline step after the migration, meaning a schema-breaking migration would apply while both nodes were still fully online, serving the *old* code against the *new* schema for the entire migration window — the exact failure a maintenance window exists to prevent. The maintenance window now covers backup → migrate → schema → deploy as one unit. The `devops` LXC — previously absent from `ansible/inventory/hosts.yml` entirely — is added as its own group and patched **last**, in its own workflow step (`continue-on-error: true`, followed by an `if: always()` confirmation step) via `--limit devops`, using a detached, 15-second-delayed self-reboot (`ansible/roles/patch`, `patch_self_reboot` computed per-host from `'devops' in group_names`) instead of the blocking `ansible.builtin.reboot` every other host uses.
* **Rationale:** `app_offline.htm` is genuinely an IIS/ASP.NET Core Module feature — this fleet runs Kestrel directly under systemd (ADR 02), which has no equivalent built in, so reproducing the convention needed real middleware, not just a file-drop. `/health`'s exemption was a mid-build correction, not the original design: the first pass made `/health` 503 too, on the theory that "Kemp should see it as down"; checking Kemp's actual `Blazor-App-VIP-80` config directly (WUI, Advanced Properties) found both `"Sorry" Server` and `Not Available Redirection Handling` unconfigured — meaning if both real servers had gone "Down" together, Kemp had nothing to fall back to, and visitors would hit Kemp's own generic error instead of ever reaching `app_offline.htm`. Keeping `/health` honest instead means Kemp requires **no configuration changes at all**: it keeps routing to a real server that happens to be serving a maintenance page for every other path, which is the actual goal. The sentinel file lives at a fixed path outside any `releases/<sha>` directory specifically because a deploy's `rsync --delete` + symlink flip would otherwise make the file vanish the moment the new release lands, silently ending the maintenance window mid-deploy. The offline/online logic itself lives in a **composite action**, not a reusable workflow (`workflow_call`) — a reusable workflow always runs as its own separate job, which can't be interleaved as a couple of steps in the middle of an existing job the way "offline → deploy/patch → online" needs; a composite action is just steps, droppable into any job at the point that needs them. This was a deliberate correction mid-build: the first pass had web offline/online implemented twice — as Ansible tasks in `patch.yml` and as raw `scp`/`ssh` steps in `deploy-blazor.yml` — which is exactly the kind of drift this repo's whole IaC/ADR discipline exists to prevent; collapsing both onto one composite action removed the duplicate copy and simplified `patch.yml` back down to a single generic play in the process. `devops` patching itself last, in a separate step with a delayed self-reboot, exists because it's the one host where the thing applying the patch and the thing running the GitHub Actions job are the same box (ADR 22) — a reboot mid-task there would kill the runner before it could report success at all; delaying the reboot ~15 seconds lets the step (and the whole job) finish and report normally first, and `continue-on-error` + the final `if: always()` step are the safety net for the rare case that timing is tighter than expected. This is a first cut, not a finished patching story: it always blanket-patches rather than checking PatchMon's dashboard first to skip hosts with nothing pending, and pinned-version application-level bumps (the other half of `LAB-RUNBOOK.md` §5's original TODO) are still unaddressed — both remain open follow-ups.

## ADR 52: web-online Must Run `if: always()` — A Real Outage, Not a Hypothetical
* **Decision:** Both `deploy-blazor.yml`'s and `patch-fleet.yml`'s "Bring both web nodes back online" step (`uses: ./.github/actions/web-online`) now carries `if: always()`.
* **Rationale:** Confirmed live, in production, the first time `deploy-blazor.yml` ran against the freshly Terraform-recreated `blazor-web-03` (ADR 50): "Take both web nodes offline" is two sequential `scp` commands in one `run:` block — the first (to `blazor-web-04`) succeeded, the second (to `blazor-web-03`) failed with `Host key verification failed` (a genuinely new container has a genuinely new SSH host key; the runner's `known_hosts` still had the old one cached for that IP from the destroyed container). GitHub Actions stops a job on a failed step by default, so every step after that — including "Bring both web nodes back online" — was skipped. Result: `blazor-web-04`, the only node actually serving traffic, sat showing `app_offline.htm` to every real visitor (`/health` `200`, `/` `503`) with nothing left in the run to ever take it back down. Manually removed the file to restore service, then closed the actual gap: `if: always()` guarantees this step runs regardless of what failed earlier in the job, and it's safe to run unconditionally — `rm -f` and a health check are both idempotent even in the (also real) case where the site was never actually taken offline. `patch.yml`'s own web tier patching has the identical shape (offline → risky work → online) and the identical gap, so it got the same fix. The stale SSH host key that triggered this specific run is now cleared (`ssh-keygen -R`); it will recur any time a node's underlying container is destroyed and recreated at the same IP (any future Terraform replace), which is a separate, still-open question about whether to auto-refresh `known_hosts` in CI or keep clearing it by hand each time.

**Addendum, confirmed live the same day:** `if: always()` alone wasn't enough — the first real `Patch Fleet` run failed inside `web-online` itself, immediately after `patch.yml`'s reboot: `curl: (7) Couldn't connect to server` at `0 ms`. The one-shot health check ran before `blazor-app.service` had time to start listening on `:5000` post-reboot; the site was fine seconds later on its own, but the workflow had already failed the step (both nodes verified healthy by hand afterward - `if: always()` had already prevented a stuck-offline outage, this was a separate, narrower gap). `web-online` now retries each node's health check up to 10 times, 3s apart (30s budget), matching the retry budget `ansible/patch.yml`'s own health task already used for the identical post-reboot race on the Ansible side.

## ADR 53: Patch Fleet Order Corrected — Web Patches Last, Comes Back Online Last
* **Decision:** `patch-fleet.yml`'s order is now: take web offline → patch+reboot every other tier (Postgres, Garnet, RabbitMQ, DNS, PKI, preview, observability, uptime-kuma, homepage, infra) → patch+reboot the web tier → bring web back online → patch devops last. Previously web patched and came back online *first*, before its own backend dependencies.
* **Rationale:** User-identified before this ever ran against real backend tiers: web's `/health` deep-checks Postgres, Garnet, and RabbitMQ connectivity (ADR 10), and Ansible patches a tier's hosts concurrently, not one-at-a-time — so under the old order, by the time Postgres/Garnet/RabbitMQ's turn came, web was already back online serving real traffic, and would have hit a live, user-visible partial outage (backend mid-reboot) *on top of* the planned maintenance window, not instead of it. The corrected order keeps web offline for the entire duration every tier it actually depends on is being patched, so any backend instability during that window is invisible to real visitors — only visible once web itself comes back online last, by which point everything it needs is already stable. This does mean a longer maintenance window than before, which is the correct trade for a manually-triggered, infrequent operation where a known, communicated outage (the maintenance page) is strictly preferable to an unpredictable one.

## ADR 58: Garnet Installed Into a Versioned Directory, `/opt/garnet` Now a Symlink
* **Decision:** Each Garnet release is copied into `/opt/garnet-{{ garnet_version }}/` instead of directly into `/opt/garnet/`; `/opt/garnet` is now a symlink to the current version's directory, swapped with `ansible.builtin.file: state=link, force=true`. A one-time migration task removes `/opt/garnet` first if it's still a real directory from before this change (`stat` + `islnk` check). `garnet.service`'s `WorkingDirectory`/`ExecStart` (both hardcode `/opt/garnet`) needed no changes.
* **Rationale:** Confirmed live — the very first real version bump this role ever went through (`docs/01` ADR 57's Garnet PR, merged and converged same session): the play failed with `OSError: [Errno 26] Text file busy: b'/opt/garnet/GarnetServer'`. Ansible's `copy` module truncate-writes changed files in place (`shutil.copyfile`) rather than write-temp-then-atomic-rename, and Linux refuses to truncate a binary the kernel currently has mapped for execution — every previous run of this role either did a fresh install (nothing running yet) or hit an unchanged version (copy no-ops, never opens the file for writing), so this exact failure mode was never exercised until an already-running host got a real bump. The symlink swap never touches the currently-executing binary's inode at all; the new version only becomes live when the already-existing restart-on-change logic (ADR 55, extended here to also key off `garnet_symlink.changed`) actually restarts the service afterward.

## ADR 60: Uptime Kuma Monitors Seeded as Code, Bypassing add_monitor()'s Broken Payload
* **Decision:** `ansible/roles/uptime-kuma`'s new tasks install a venv (`/opt/uptime-kuma-seed`), pin `uptime-kuma-api==1.2.1`, and run `files/seed_monitors.py` against `uptime_kuma_monitors` (`ansible/inventory/group_vars/uptime_kuma.yml`) — one monitor per fleet service, idempotent by name. The script does **not** call the library's own `add_monitor()`; it builds the payload via the library's internal `_build_monitor_data()`, adds `conditions: []` itself, then calls the library's lower-level `_call('add', data)` directly. Gated on `uptime_kuma_username`/`uptime_kuma_password` being defined (same graceful-skip idiom as the `technitium` role) — this instance's admin account was created by hand through Kuma's first-run wizard, so Ansible only ever reads those values from `/opt/ansible-secrets/all.yml`, never generates or sees them typed anywhere.
* **Rationale:** Confirmed live against a real request first: Uptime Kuma has no native REST write API at all (monitor creation is Socket.IO-only, per an open upstream feature request); `uptime-kuma-api` is the only maintained-ish Python wrapper for that Socket.IO interface, but its last release was September 2023 and its own compatibility table stops at Kuma 1.23.2 — this repo pins Kuma 2.5.3. Tested `login()` + `add_monitor()` live against the real instance: login succeeded (the Socket.IO handshake survived the version jump), but `add_monitor()` failed outright — `SQLITE_CONSTRAINT: NOT NULL constraint failed: monitor.conditions`. Pulled Kuma 2.5.3's own server source (`server/server.js`'s `socket.on("add", ...)` handler) and found the exact cause: `monitor.conditions = JSON.stringify(monitor.conditions)` — Kuma 2.x added a `conditions` column (its conditional-alerting feature) that the 2023-era library never learned about, so it never sends the field, `JSON.stringify(undefined)` is `undefined`, and the resulting NULL violates the schema. Checked whether `conditions` could just be passed as an extra kwarg to the library's own `add_monitor(**kwargs)` — no: `_build_monitor_data()` has a fixed, explicit parameter list with no `conditions` parameter and no catch-all, so there's no legitimate way to pass it through the public surface. Reusing the library's own internals to complete the one broken field (rather than writing a full raw Socket.IO client from scratch, or depending on the library's crippled default) was verified live end-to-end — create, list, delete all confirmed working against the real instance — before landing this.

## ADR 61: Authentik Fronted by Its Own Caddy on 443, Not an Embedded Listener on 9443

Building the actual role surfaced real uncertainty that pattern doesn't resolve: Authentik's `cert_discovery_dir` config key is documented as importing certificates as manageable objects for other features (e.g. SAML signing), not necessarily wiring up the core web server's own listening TLS certificate - and nothing in the pinned version's shipped `default.yml` clarifies the two are the same mechanism. ## ADR 63: Authentik Moved to pve4, Trimmed 8192→3072MB — pve3 Physically Couldn't Fit It
* **Decision:** `authentik` in `terraform/lxc.tf` moves from `node = var.proxmox_node_2` (pve3) to `var.proxmox_node_1` (pve4), VMID 324→417 (matching this repo's own node-in-VMID convention), and memory trims from 8192MB to 3072MB (swap set to 3072MB). Even after this, pve4's LXC memory limits sum to more than its 16GB physical RAM — a real, deliberately accepted overcommit, documented here rather than silently left as an undocumented risk.
* **Rationale:** Caught by GitHub Copilot's review on PR #7 (a RabbitMQ-only change) flagging that pve4's allocations summed to exactly 16384MB — no headroom for the hypervisor itself. Checking the actual math turned up something worse: pve3 (documented as 4 vCPU / **8GB RAM**) was carrying `authentik`'s original 8192MB allocation *alone* equal to the entire node's physical capacity, on top of 8704MB already committed to other pve3 tenants (itself already ~6% over physical before Authentik) — pve3's total came to 16896MB against 8192MB actually available, more than double. This was a placement mistake made when ADR 59 copied community-scripts' generic 8GB default onto whichever node felt narratively right (pve3, alongside the other VLAN 130/mgmt-tier LXCs) without checking it against that node's real physical capacity - a more basic error than the "should this be trimmed" question ADR 59 actually considered. Moved to pve4 (the higher-capacity node, already hosting Postgres/the preview host) and trimmed to 3072MB: Authentik's own docs cite ~2GB as viable for small deployments, and this instance's steady-state footprint should run lighter than community-scripts' 8GB default assumes, since it reuses the shared postgresql/garnet LXCs (ADR 59) rather than running a self-contained Postgres+Redis stack alongside it. Swap stays generous as headroom for the one-time cargo/pnpm build spike specifically. Deliberately did **not** chase pve4's remaining overcommit further by trimming other already-tuned services (garnet, infisical, etc.) — each of those would need its own justification and carries its own regression risk, and RabbitMQ's OOM (ADR 62, this same session) already established what the actual trigger for revisiting a specific allocation looks like: a confirmed-live incident, not a preemptive guess. Correction from Copilot's review on this PR: each LXC's `memory` value is a hard per-container cgroup limit, not a soft one — RabbitMQ's own OOM-kill (ADR 62) is direct proof a container gets killed the instant it tries to exceed its own limit. What's *not* reserved is host RAM in advance: the limits aren't pre-allocated chunks, so their sum can exceed physical capacity as long as actual concurrent usage across all containers doesn't. The sum exceeding physical RAM is therefore a risk to monitor (Cockpit/PatchMon) for any single container creeping toward its own limit, not a guaranteed failure — but it's a hard wall for whichever container hits it, not a soft one.

## ADR 65: Authentik's First Real Build — Five Environment-Mismatch Bugs Found and Fixed, Confirmed Live End-to-End
* **Decision:** Fixed five real bugs surfaced by actually running the Authentik role against the live LXC for the first time (all in `ansible/roles/authentik/tasks/main.yml` unless noted), then manually validated the *entire* build and boot sequence end-to-end before landing anything: `libunwind-18-dev` → `libunwind-dev` (that exact versioned package doesn't exist in Debian 12's repos); `pnpm.cjs` → `pnpm.mjs` and `dist/index.html` → `dist/admin` (both `creates:` idempotency guards referenced paths that don't actually exist in this pnpm/build output); added a Go 1.27.0 install (read from the source's own `go.mod`) - not for the LDAP/RAC/Radius outposts this role deliberately skips, but because `cargo build`'s transitive `aws-lc-fips-sys` dependency shells out to `go` for its own CMake codegen; `./autogen.sh` → `./configure` in the xmlsec build (the release tarball ships a pre-generated `configure`, not the autotools-regenerating script community-scripts' git-checkout-based install uses); added `UV_PYTHON_INSTALL_DIR=/usr/local/uv-python` to the `uv sync` task (without it, `uv` running as root installs its managed Python under `/root/.local/share/...`, which the unprivileged `authentik` service user can't traverse at all - "Permission denied" the instant the service tries to exec it). ## ADR 66: Tier-2 Forward-Auth Wired for Five Apps via Authentik's Embedded Outpost

Homepage's pre-existing public Cloudflare Tunnel route (`homepage.smartsoftwarecoffee.com`, ADR 47) is untouched — it still hits port 3000 directly, bypassing this new internal-only Caddy front entirely.

## ADR 68: Forward-Auth Routing Fixed, Confirmed Live — Access Gate Itself Still NOT Enforcing (Open)
* **Decision:** Two real, confirmed-live bugs fixed in the ADR 66 Caddy templates (`roles/caddy-forward-auth/templates/Caddyfile.j2`, `preview-host/templates/ops.caddy.j2`): (1) `forward_auth`'s upstream is a different hostname (`https://authentik.{{ internal_domain }}`) than the site itself, and Caddy rewrites the outbound `Host` header to match that dial address by default — Authentik never learned which app was actually being requested and 404'd the check every time. Fixed with `header_up Host {http.request.host}` inside the `forward_auth` block. (2) The whole site block is now wrapped in an explicit `route { }`, with a new leading `reverse_proxy /outpost.goauthentik.io/* ...` passthrough — both missing before, both present in Authentik's own official Caddy documentation template, and required for the OAuth callback that completes login to have anywhere to land. Separately, the embedded outpost's own `authentik_host`/`authentik_host_browser` config (`GET /api/v3/outposts/instances/<pk>/`) was blank — set to `https://authentik.{{ internal_domain }}` live via the API, which also explains an earlier-observed broken `http://localhost/application/o/authorize/...` redirect URL.
* **Still open, NOT fixed:** even with all of the above, a fully unauthenticated request (confirmed via `curl` with zero cookies from a separate process, AND via a real Chrome browser with a clean, verified-empty cookie jar) still gets waved straight through the auth check to the real backend app, instead of being redirected to Authentik's login flow. Ruled out as the cause, each confirmed live: (a) binding an explicit `require-authenticated-user` expression policy to the Application (no change); (b) `forward_single` mode instead of `forward_domain` (identical bypass, so it isn't domain-mode-specific); (c) `skip_path_regex` being empty and somehow matching every path (set to a deliberately non-matching regex, no change); (d) a stale/leftover session cookie from earlier manual testing (curl's request is provably cookie-free; the real browser's cookie jar was checked and contained no Authentik cookie). Until this is resolved, **these five apps are not actually access-gated** — Caddy/TLS/routing all work correctly, but anyone who can reach the URL gets straight through.
* **Rationale:** Found and fixed via the same "confirmed live" discipline as every other ADR here — Chrome browser testing (at the user's specific request, to rule out `curl` as a testing artifact) reproduced the identical bypass a stateless `curl` request showed, which is what gave confidence this is a real gap rather than a methodology error. Research into upstream GitHub issues turned up a cluster of open, unresolved proxy/outpost authentication bugs specific to the 2026.8.x release line (`goauthentik/authentik` issues #26125, #26076, #26270, among others) — none is an exact match for this specific symptom, but the pattern (multiple independent, still-open auth-path regressions clustered around this exact version) is strong circumstantial evidence this may be an upstream bug rather than a configuration gap, though that is not confirmed. Deliberately stopped guessing further at this point rather than continue an unbounded trial-and-error search; likely next steps for whoever picks this up are pinning to a different `authentik_version` known not to exhibit this, or filing/searching further for the exact upstream issue.
* **Also fixed as this app was cleaned up:** Homepage's `HOMEPAGE_ALLOWED_HOSTS` (env.j2) would have rejected the new Caddy front's Host header (`homepage.{{ internal_domain }}`, no port) even once auth is fixed — added. PatchMon's own `CORS_ORIGIN` (`patchmon.env.j2`, still `http://{{ ansible_host }}:{{ patchmon_port }}`) will similarly reject requests via `https://patchmon.{{ internal_domain }}` once the auth gate is closed — **not yet fixed**, tracked here as a known follow-up alongside the auth gate itself.

## ADR 69: terraform-plan.yml Gains an Optional `-replace` Input
* **Decision:** `terraform-plan.yml`'s `workflow_dispatch` gains an optional `replace_target` input. When set, the plan step runs `terraform plan -replace=<address>` instead of a plain plan; when blank, behavior is unchanged. The Step Summary (ADR 64) notes the replace target when one was used, so a reviewer sees it's a forced-replace plan, not a normal one.
* **Rationale:** `unifi_firewall_policy.drop_preview_to_mgmt` (ADR 59/61) needed exactly this — a controller-assigned index recovery via `terraform apply -replace=...` — and, before this ADR, the only way to run it was `terraform apply -replace=...` typed directly on the devops LXC: `terraform-apply.yml` only ever applies a plan artifact `terraform-plan.yml` already produced (ADR 22, "never a plan regenerated at apply time"), and that plan step took no extra flags, so a `-replace` could never flow through the reviewed-plan-then-approved-apply pipeline at all. Confirmed live this session: the sandbox's own IaC-apply protection correctly refuses to let an agent run `terraform apply` directly, for good reason — this is exactly the kind of state-mutating action that deserves the same reviewed-plan-then-human-approval gate as everything else in `terraform-apply.yml`, not a bespoke direct-SSH exception. Extending `terraform-plan.yml` (rather than special-casing `terraform-apply.yml`) keeps `terraform-apply.yml` exactly as narrow as ADR 22 intends — it still only ever applies whatever `terraform-plan.yml` produced, `-replace` included.

## ADR 71: ADR 68's "Anonymous Bypass" Root-Caused and Fixed — a Port in the Host Header
* **Decision:** `header_up Host` in every `forward_auth`/outpost-passthrough block (`roles/caddy-forward-auth/templates/Caddyfile.j2`, `preview-host/templates/ops.caddy.j2`) now sets a bare hostname (`authentik.{{ internal_domain }}`, no port) instead of `{http.request.host}` or Caddy's own default. **This closes ADR 68.** All five tier-2 apps are now confirmed-live actually access-gated, not just routed.
* **Rationale:** Found by reading Authentik's own Rust outpost source (`goauthentik/authentik`, `src/outpost/proxy/mod.rs`) after exhausting config-level guesses (documented in ADR 68). `ProxyOutpost::lookup_app(host)` is what selects *which* of the five providers should handle a given `forward_domain` request: it tries an exact host match first, then falls back to checking `host.ends_with(cookie_domain)` across every `forward_domain` provider. The `host` it checks is the **literal incoming HTTP `Host` header** of the connection Caddy makes to Authentik — and Caddy's own default, when the upstream is specified as a bare URL (`forward_auth https://authentik.{{ internal_domain }}`), sets that header to the **dial address including the port** (`authentik.brewhouse.internal:443`). `"authentik.brewhouse.internal:443".ends_with("brewhouse.internal")` is `false` — the trailing `:443` breaks the suffix match for every single provider. `lookup_app` returns `None`, `app_for_request` returns `None`, and the request silently falls through to Authentik's own **core backend** (the same process, embedded) instead of ever reaching the outpost's forward-auth logic (`check_auth`/`is_allowlisted`/`auth_start`) at all — which is why it read as an unconditional "let everything through": the auth check was never actually running. The core backend then just serves whatever its own Django URL router happens to return for an unrecognized path (a real page for some paths, a 404 for others), which is what produced the inconsistent, confusing symptoms chased throughout ADR 68 (200s, 404s, policy bindings and `skip_path_regex` changes that provably did nothing because none of that code was ever being reached). Confirmed live, methodically: manually reproducing Caddy's exact `X-Forwarded-*` headers via `curl` against Authentik directly got a correct `302` whenever the literal `Host` header curl sent omitted the port (curl's own default for a portless `https://` URL) and reverted to the broken behavior only when the `Host` header included `:443` — isolated by diffing Caddy's own debug-log dump of the real outbound request against a manually reconstructed one, header by header, until the port was the only remaining difference. Verified end-to-end afterward with a real browser: `https://patchmon.brewhouse.internal/` now correctly redirects to `Welcome to authentik! Log in to continue to PatchMon` (previously it went straight through, or — before this exact fix — attributed to the wrong provider's client, see caveat below).
* **Known caveat, not fixed here:** because all five providers share `cookie_domain: {{ internal_domain }}` with no host that exactly matches "authentik.{{ internal_domain }}", `lookup_app`'s suffix-match fallback is inherently ambiguous when several providers tie on domain length (all five do) — Rust's `HashMap` iteration order for that fallback loop is stable within one running process but arbitrary across restarts, so which provider's OAuth client/session cookie namespace actually "wins" for a first-touch login can vary per outpost restart. In practice this still requires a real login and still gates access correctly (confirmed live above), just not necessarily always attributed to the specific app the user first visited. A cleaner fix (giving each provider a truly unique `external_host` the literal Host header can exact-match, or accepting session-per-first-provider as the real cross-app SSO model) is a follow-up, not required to close the actual security gap ADR 68 opened.
  **Follow-up investigated (ADR 73's session) and deliberately not pursued further:** tried forwarding each app's own bare hostname (e.g. `header_up Host patchmon.{{ internal_domain }}` instead of the shared `authentik.{{ internal_domain }}`) specifically to hit `lookup_app`'s **exact**-match path instead of the ambiguous suffix-match fallback. Confirmed live this makes it *worse*, not better: the exact-match path returns the same bare `200` anonymous-bypass ADR 68 already fixed, even with fully correct `X-Forwarded-Host`/`Proto`/`Uri` headers alongside it — a separate bug in Authentik's exact-match code path, distinct from the port-in-Host bug this ADR fixed for the suffix-match path. The current shared-identity approach isn't a compromise being tolerated for convenience; it's the only one of the two `lookup_app` code paths that's actually confirmed to enforce authentication at all. Not investigating further validates ADR 68's fix was the right one to land and ship, rather than a symptom of a still-deeper problem.

## ADR 72: Tier-1 Native OIDC Rollout Begins — Grafana First
* **Decision:** First of six tier-1 apps (`docs/S3-01`'s own scope: Grafana, Portainer, Proxmox, Infisical, pgAdmin, RabbitMQ). Created an OAuth2/OpenID Provider + Application in Authentik for Grafana (`authorization_code`+`refresh_token` grants, `openid`/`email`/`profile` scope mappings, confidential client, redirect URI `http://10.10.130.118:3000/login/generic_oauth`). `roles/observability` gained a new task writing `GF_AUTH_GENERIC_OAUTH_*` into `/etc/default/grafana-server` (Grafana's own env-var config override mechanism — no `grafana.ini` template needed), gated on `grafana_oidc_client_id`/`grafana_oidc_client_secret` being defined, same graceful-skip idiom as `uptime_kuma_username`. ## ADR 73: Tier-1 Native OIDC Completed — Remaining Five Apps
* **Decision:** Closes the tier-1 milestone ADR 72 opened. Authentik-side OAuth2 Provider + Application created for each of the five remaining apps (Portainer, Proxmox, Infisical, pgAdmin, RabbitMQ). App-side wiring varies by how each app actually exposes its own OIDC config:
  - **pgAdmin**: fully Ansible-managed. A new `config_local.py` (pgAdmin's own documented override point — too complex for a plain env var, unlike `PGADMIN_DEFAULT_EMAIL`/`PASSWORD`) is mounted into the container, gated on `pgadmin_oidc_client_id`/`_secret` being defined. Also needed: the step-ca root CA mounted into the container with `REQUESTS_CA_BUNDLE` set — confirmed live, pgAdmin's OAuth2 client (Python `requests`) doesn't trust our private root by default, throwing `SSLCertVerificationError` fetching Authentik's OIDC discovery document until fixed.
  - **RabbitMQ**: fully Ansible-managed. `rabbitmq_auth_backend_oauth2` plugin + `rabbitmq.conf` entries follow Authentik's own official RabbitMQ integration guide verbatim (a custom `RabbitMQ claims` scope mapping emitting `aud: ["rabbitmq"]` and the user's `groups`, plus `auth_oauth2.scope_aliases` mapping two new Authentik groups — `rabbitmq-administrator`/`rabbitmq-monitoring` — to RabbitMQ's own permission tags). Needed two more fixes beyond the guide, both confirmed live: (1) the same step-ca CA-trust gap as pgAdmin, fixed by installing the root cert into the LXC's system trust store; (2) RabbitMQ's own OIDC client library requires `crypto.subtle` for its PKCE code challenge, which browsers only expose in a secure context — the management UI was plain HTTP with no TLS at all, so login failed client-side with `Crypto.subtle is available only in secure contexts (HTTPS)` before any request even reached Authentik. Fixed by adding a plain (non-forward-auth) Caddy TLS front at `rabbitmq.{{ internal_domain }}`, same step-ca ACME pattern as `roles/authentik`'s own Caddy block.
  - **Portainer** and **Infisical**: NOT Ansible-managed — both apps' OAuth/SSO settings live entirely behind their own admin-UI (Settings → Authentication), and both apps' admin accounts are human-managed (created via first-run wizard, same boundary as `uptime_kuma_username`/`password`, ADR 60) — Ansible/this session has no credential to complete the app side. Authentik's side is ready (Provider/Application created, redirect URIs registered); manual connection steps for both are documented in `LAB-RUNBOOK.md` §6 with the exact values to paste in.
  - **Proxmox**: configured directly via `pveum realm add ... --type openid`, live on `pve1` — deliberately NOT Ansible-managed (ADR 22 keeps Proxmox itself outside Terraform/Ansible's scope entirely; this follows that boundary, done as a one-time manual command same as the existing cross-node SSH trust fix). Needed the same two fixes as the container-based apps: pve1 had no DNS route to `authentik.{{ internal_domain }}` at all (a physical host, never covered by ADR 67's fleet-wide resolver play, which only reaches Ansible-managed LXCs) — fixed with a one-line `/etc/hosts` entry; and pve1 didn't trust step-ca's root CA either — fixed by importing it into the system trust store, same as RabbitMQ/pgAdmin. `--default 0` keeps `pam`/`root@pam` as the default login realm — the same "new SSO path alongside existing break-glass access, not replacing it" discipline ADR 10 already established for Kemp.
  - All six apps' `root@pam`-equivalent local admin accounts stay untouched and available — this is additive SSO, not a replacement for any existing login path.
* **Rationale:** Confirmed live for all six (Grafana in ADR 72, the other five here): each app's own login page/button correctly redirects to Authentik and lands on that app's own "Log in to continue to `<App Name>`" prompt — proof the OIDC client_id/redirect_uri pairing is genuinely correct per app, not a shared/ambiguous identity the way ADR 71's tier-2 forward-auth caveat describes (tier-1 OIDC is a direct client_id-keyed flow with no domain-suffix-matching step, so that specific ambiguity class doesn't apply here at all). Three of the five real bugs found this pass are the exact same root cause wearing different clothes — **step-ca is a private root CA and nothing outside the Ansible-managed fleet or its own Caddy fronts was ever told to trust it** — worth remembering as the first thing to check the next time any new service's outbound HTTPS call to `*.{{ internal_domain }}` fails with a certificate error. None of the six logins were completed with real credentials in this session (the assistant doesn't type passwords into forms, human-chosen or otherwise) — the redirect-to-correct-provider proof is the security-relevant confirmation; a full click-through login is worth doing once by a human to see the post-login landing page for each.
