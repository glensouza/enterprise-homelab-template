## ADR 29: Infisical Agent Install Moved Into Ansible, Surfaced a Firewall-Ordering Bug
* **Decision:** A new `infisical-agent` role, added to the `web` play, replaces what was a fully manual per-LXC block in `LAB-RUNBOOK.md` step 8 (install the CLI package, hand-write `client-id`/`client-secret`/`agent-config.yaml`, install a systemd unit). Getting it working live surfaced two real bugs, both now fixed at the source rather than worked around: (1) these minimal LXC images have no `curl` — `curl ... | bash` was silently "succeeding" doing nothing, because a pipeline's exit status is its *last* command's (`bash`, which exits 0 on empty stdin), not `curl`'s; the role now installs `curl` first. (2) `terraform/unifi.tf` never had a rule allowing VLAN 110 (web) to reach the Infisical LXC on `8080` at all — added one, but a first attempt still failed: `unifi_firewall_policy`'s `index` field is controller-assigned and **read-only** (confirmed via the provider's own schema), so the new allow rule was simply appended after the pre-existing `drop_web_to_mgmt` rule regardless of Terraform's `depends_on` (which only orders API calls during apply, and doesn't touch the index of a resource that isn't itself being changed). Fixed with `terraform apply -replace=unifi_firewall_policy.drop_web_to_mgmt`, forcing it to be destroyed and recreated so the controller assigns it a fresh, later index.
* **Rationale:** Same reasoning as ADR 26/27 — `ansible-playbook site.yml` should finish with the app *actually able to start*, not "mostly done, now SSH in three more times by hand." Both bugs were things no amount of re-reading the Ansible/Terraform code would have caught — the curl gotcha only shows up as a pipeline that reports success while doing nothing, and the firewall-ordering gotcha only shows up as a connection that still times out after the "fix" is already applied. Worth documenting `docs/05`'s firewall table with the `index`-ordering caveat specifically, since any *future* allow rule added against an already-existing drop rule on the same source/destination pair will hit the identical bug.

## ADR 32: First-Ever Approved Deploy Surfaced Two Real, Pre-Existing CI Bugs
* **Decision:** `deploy-blazor.yml`'s `Restore & Test` step gates every deploy on the full test suite, including an Aspire-orchestrated integration test that starts the whole local app graph (Postgres, Garnet, RabbitMQ) via DCP. The first time any deploy run ever got past the `production` environment's required-reviewer gate (this session), it failed — a gap nobody had hit before because nothing had ever been approved. Two independent, confirmed-live bugs, both now fixed at the source: (1) **`BrewHouse.AppHost/Program.cs`'s Garnet resource referenced `ghcr.io/microsoft/garnet`, which Aspire's DCP cannot pull** ("pull access denied ... repository does not exist") even though a plain `docker pull` of the identical reference succeeds — a DCP/GHCR-specific incompatibility, not a real permissions problem. Fixed by referencing a registry-less local tag (`microsoft/garnet`) instead, with `deploy-blazor.yml`/`pr-preview.yml` each pre-pulling from `ghcr.io` and re-tagging locally as a step before tests run, so the workaround is self-healing rather than a one-off manual fix that silently breaks the next time the runner's Docker state resets. (2) **Aspire's `AddRedis()` resource type injects its own `redis-server` startup command regardless of which image is substituted in** — Garnet's image only has `/app/GarnetServer`, so the container crashed with exit code 127 ("redis-server: not found") every single time, invisibly, because DCP's own resource-creation timeout (a fixed internal window, independent of any test-level Polly timeout) always expired first with a generic `TaskCanceledException` that named neither bug. `.WithEntrypoint("/app/GarnetServer")` fixes it.
* **Rationale:** Both bugs were undiagnosable from the CI failure message alone (`Polly.Timeout.TimeoutRejectedException`, no mention of Garnet, GHCR, or exit codes anywhere) — confirmed only by running the AppHost directly on the runner outside the test harness and reading DCP's own debug-level logs (`Logging__LogLevel__Aspire=Debug`), then binary-searching resource-by-resource with `docker ps -a` to find which one never even got a container. Neither bug is specific to production (the real Garnet LXC deployment from ADR 27 is unaffected — separate binary, separate systemd unit, no Aspire/DCP involved at all) — this only affects the local-dev/CI-testing AppHost path (ADR 14).

## ADR 37: Web -> PatchMon Firewall Exception, Same Ordering Bug as ADR 29
* **Decision:** Added `unifi_firewall_policy.web_to_patchmon`, allowing VLAN 110 (web) to reach the `patchmon` LXC (`10.10.130.122`) on `3000`, and added it to `drop_web_to_mgmt`'s `depends_on` alongside `web_to_infisical` so it evaluates first.
* **Rationale:** Confirmed live: a manual `curl` from `blazor-web-01` straight to `/api/v1/auto-enrollment/enroll` hung until timeout (exit 124) rather than failing fast, and the `patchmon-agent` role's own "Enroll this host with PatchMon" task failed the same way against both web LXCs. `drop_web_to_mgmt` blocks all of VLAN 110 -> VLAN 130 by default, and — exactly as in ADR 29 for Infisical's `8080` — no exception for PatchMon's `3000` had ever been added, because nothing on that port was reachable (or needed) until ADR 34 added fleet-wide agent enrollment. Applied with `terraform apply -replace=unifi_firewall_policy.drop_web_to_mgmt` per the same `index`-is-read-only caveat ADR 29 already documented, so the new allow rule doesn't just get appended after the existing drop rule. This does not explain the separately-reported duplicate/offline `garnet` host records in PatchMon's dashboard — VLAN 120 (data, where `garnet` lives) has no equivalent blanket block to VLAN 130, so those enrollments got far enough to create pending host records; that symptom is more consistent with the install script's 5-minute bootstrap-token window expiring, and is tracked separately.

## ADR 39: PatchMon Agent Install Hung on `read -r response` Under Ansible's Allocated PTY
* **Decision:** Changed `patchmon-agent`'s "Run the PatchMon agent install script" task from `ansible.builtin.command: sh /tmp/patchmon-install.sh` to `ansible.builtin.shell: sh /tmp/patchmon-install.sh < /dev/null` with `timeout: 120`.
* **Rationale:** Confirmed live: the fleet-wide Ansible Converge run (34906618598) hung for the CI job's entire remaining runtime with zero new log output after `TASK [patchmon-agent : Download the PatchMon agent install script]`, blocking the shared self-hosted runner. Checking the actually-downloaded `/tmp/patchmon-install.sh` on the still-running hosts (`sh /tmp/patchmon-install.sh`, sleeping, no open sockets, no CPU use — not a network hang) found the script does `# Check if we can read from stdin (interactive terminal)` followed by `read -r response` when it detects a pre-existing half-installed/failed dpkg entry. The role's own top-of-file comment claimed this was "confirmed live" to behave non-interactively — true for the `curl url | sh` invocation that comment was actually tested against, where stdin is a real non-tty pipe, but Ansible's ssh connection plugin allocates a pty (`-tt`) for every `command`/`shell` task in this setup regardless of `become` (confirmed by inspecting the runner's own live ssh child processes), so stdin for the *downloaded-then-executed* script is a tty after all, and its interactive-detection heuristic reads it as such. Redirecting from `/dev/null` forces immediate EOF on that `read`, taking the same non-interactive path the original comment assumed; `timeout: 120` is a safety net against any other unforeseen prompt in a script this repo doesn't control the source of. Cancelled the hung run (`gh run cancel`) and killed five leftover `sh /tmp/patchmon-install.sh` processes across `blazor-web-01/02`, `garnet`, `infisical`, and `technitium-dns` that outlived the cancelled SSH connections — the same "orphaned process from an interrupted Ansible run" hygiene gap as earlier this session, just triggered by a real script bug instead of a manual background task.

## ADR 40: Home Network Outage After Firewall Applies — UniFi Restored, Firewall Scope Narrowed, PatchMon Reachability Fixed Fleet-Wide
* **Decision:** After a home-network-wide outage (every Windows device, wired and wireless, stuck on `169.254.x.x` APIPA addresses) forced a restore of the UniFi controller from a 2-week-old backup, three things changed: (1) removed `pve1_to_nas`/`pve2_to_nas`/`pve3_to_nas`/`pve4_to_nas`/`mgmt_to_nas`/`data_to_nas_nfs`/`data_to_nas_nfs_portmapper` from `terraform/unifi.tf` entirely — none had a current consumer, confirmed live (see rationale); (2) added `preview_to_patchmon` (VLAN 140 → `10.10.130.122:3000`) and added it to `drop_preview_to_mgmt`'s `depends_on`, mirroring `web_to_patchmon` (ADR 37) — PatchMon reachability is now explicit for every tier (VLAN 110 via the explicit rule, VLAN 120 via the same-zone default-allow with no drop rule against it, VLAN 130 intra-zone, VLAN 140 via this new rule).
* **Rationale:** The outage was discovered days after `web_to_patchmon` and a `-replace` of `drop_web_to_mgmt` were applied (ADR 37) — both used the pattern of destroying and recreating the catch-all BLOCK policy to force it to re-evaluate after a new ALLOW, since `unifi_firewall_policy`'s `index` is controller-assigned and read-only. Disabling Terraform-created firewall rules from a still-connected Mac partially restored wired connectivity, which is real (if circumstantial) evidence the firewall policy set was at least implicated; a full UniFi backup restore was needed to fully resolve it, and Wi-Fi didn't recover until the next day. No `unifi_network` resource in this repo has DHCP enabled on any of the four managed VLANs, and none of them is the user's own LAN/Wi-Fi network, so there's no *direct* mechanism here for a VLAN config change to hand out APIPA addresses — if Terraform's changes were a cause at all, it would have to be the zone-based firewall policy compile/push destabilizing the gateway broadly enough to affect DHCP servicing platform-wide, not a targeted config change; the controller's own event log for that window wasn't recoverable (see below), so this can't be confirmed as definitive root cause, only as the most credible mechanism given what's known.
  The restore itself surfaced two further problems. First, the `terraform` UniFi service account's stored credentials stopped authenticating entirely (403 on every `terraform plan`) — the account was created or last had its password rotated more recently than the 2-week-old snapshot, so the restore rolled it back out of existence; the user recreated it by hand. Second, once auth was restored, `terraform plan` showed **28 to add, 0 to change, 1 to replace** — every single Terraform-managed `unifi_network` and `unifi_firewall_policy` resource, not just the two from ADR 37, meaning the restore wiped this repo's *entire* UniFi footprint back to whenever that snapshot was taken, not merely the most recent changes.
  With everything being recreated from scratch anyway, this was the moment to fix scope rather than reapply it as-is. Auditing all 22 firewall policies against "does this govern traffic between things this repo actually creates" found `pve1_to_nas`/`pve2_to_nas` had no current consumer, `mgmt_to_nas` had no current consumer (no VLAN 130 LXC touches the NAS), and `data_to_nas_nfs`/`data_to_nas_nfs_portmapper` (VLAN 120 → NAS) had no current consumer either — the actual bind-mount traffic (`postgresql`'s `homelab-postgres-data`, `blazor-web-01/02`'s `homelab-media`) is sourced from the Proxmox **host's** own `10.10.10.x` address (host-level `/etc/fstab`, not guest-initiated, confirmed by the user: `lxc -- mount --> pve`, `pve -- mount --> nas`), and is CIFS now, not NFS (see below) — so those two rules' ports (111/2049) were already stale regardless. `pve3_to_nas`/`pve4_to_nas` were initially kept rather than removed outright, since unlike the other five they appeared to gate traffic two currently-running LXCs actually depend on and removing them without testing first risked trading one self-inflicted outage for another. Applied everything else (24 resources: 4 VLANs, 18 firewall policies, the new `homepage` LXC) with `pve3_to_nas`/`pve4_to_nas` commented out as an explicit test, then confirmed live: `postgresql` was `active` and serving real databases, and `blazor-web-01`'s media share was mounted and browsable — both with **no rule for pve3/pve4 → NAS in place at all**. Root cause of why it was never needed: pve1-4 and the NAS all sit on the same pre-existing `10.10.10.0/24` LAN segment, so that traffic never crosses the gateway's routing/firewall boundary in the first place — a zone-based policy for it was never going to do anything either way, on any of the four Proxmox nodes. The original "access denied by server" note that motivated adding these rules in the first place was almost certainly a NAS-side share-permission issue, not a firewall one. Deleted all four `pveN_to_nas` policies outright once confirmed, rather than leaving them commented out. Separately, investigating the earlier stuck-CI incident (ADR 39) had already found `pr-preview` fatally failing PatchMon enrollment because `drop_preview_to_mgmt` blocked it with no exception carved out — same class of gap as ADR 29/37, now closed the same way.
  Finally, added `terraform/unifi-backup.sh` and a step in `terraform-apply.yml` that runs it before `terraform init`'s apply — it logs into the UniFi OS Console's own API (`/api/auth/login`, extracting the `X-CSRF-Token` response header), triggers `POST .../cmd/backup`, and downloads the resulting `.unf` file to `/opt/unifi-backups/` (outside any git checkout, ADR 35 pattern) with a UTC timestamp. Confirmed live this session end-to-end (login, CSRF, backup command, and downloading a real ~18MB file) before wiring it in. The whole point of this ADR was "we didn't have a recent backup when we needed one" — this makes that structurally impossible for any future `terraform apply` in this repo, CI or manual. **Restore procedure, confirmed live separately (2026-09-19):** these files do **not** appear in the UniFi console's own Settings → Backups list (that list only tracks the controller's own `Auto (Weekly)`/`Back Up Now` snapshots — `cmd/backup` is a different, parallel mechanism) — restoring one means Settings → Backups → **Restore** → **Upload Backup File**, not picking from that dropdown. Worth remembering under pressure: the obvious-looking restore path in the UI won't show these backups at all.

## ADR 42: PostgreSQL Never Accepted Remote Connections — Masked for Months by Earlier CI Failures
* **Decision:** The `postgres` role now explicitly configures remote access: a new `listen-addresses.conf.j2` drop-in (`{{ postgres_conf_dir }}/conf.d/listen-addresses.conf`, following the same `conf.d` pattern the pgBackRest WAL-archiving config already used) sets `listen_addresses = '*'`, and a new `ansible.builtin.blockinfile` task appends scoped `host ... scram-sha-256` entries to `pg_hba.conf` from a new `postgres_allowed_networks` var (`group_vars/postgres.yml`): the web VLAN (`10.10.110.0/24`, the app's own runtime connection), the preview VLAN (`10.10.140.0/24`, pgAdmin), and the devops LXC specifically (`10.10.10.111/32`, the only host running the self-hosted GitHub Actions runner that executes the EF migration bundle) — not a blanket "trust the LAN" rule. Both tasks are placed immediately after "Enable and start PostgreSQL" and flush their `restart postgresql` handler before the role's role/database-creation tasks run, so everything downstream in the same play already has a Postgres that accepts remote auth.
* **Rationale:** Confirmed live: the first Deploy Blazor run to ever get past both the DCP/Polly test flake (ADR 32) and the `dotnet-ef`-not-on-`PATH` bug (this session, undocumented as its own ADR since it's a one-line CI fix) failed at "Execute Migration Bundle" with a raw `Connection refused` (not an auth error) from `10.10.120.110:5432` — `ss -tlnp` on the Postgres LXC showed it bound only to `127.0.0.1`/`::1`, and `pg_hba.conf` only had `127.0.0.1/32`/`::1/128` entries, both Debian package defaults the `postgres` role (ADR 30) had never overridden. This was a genuine, always-present bug, not environment drift: the role has always handed out `EFBUNDLE_CONNECTION` and `ConnectionStrings__brewhousedb` using the LXC's real LAN IP, which could never have worked for either CI or the running app itself — it was simply unreachable as a failure mode until this run, since every previous deploy attempt died at an earlier step first. The relevant UniFi firewall policies (`web_to_postgres`, `preview_to_postgres`) already existed and passed traffic through cleanly (confirmed via a raw `/dev/tcp` connect attempt returning `Connection refused`, not a timeout — proof the packet reached the host) — this was purely a Postgres-side bind/auth gap, not a network one. Scoping `pg_hba.conf` to exactly the three networks that actually need access (rather than the whole `10.10.0.0/16` or similar) keeps this consistent with ADR 40's "narrow to what's actually needed" firewall philosophy, just applied one layer up the stack. Applied directly via `ansible-playbook site.yml --limit postgres` from the devops LXC (not through the full CI pipeline) and confirmed idempotent on a second run (`ok` on both new tasks) plus a live TCP connect test before re-triggering the deploy.

## ADR 43: `blazor-app` Role Installs `rsync` — Another Failure Masked Until the Postgres Fix (ADR 42)
* **Decision:** Added an `ansible.builtin.apt` task to the `blazor-app` role installing `rsync`, before the release/config directory tasks.

## ADR 44: `BrewHouse.csproj` Missing `WolverineFx.RuntimeCompilation`, Masked by the Test Project Referencing It Separately
* **Decision:** Added `<PackageReference Include="WolverineFx.RuntimeCompilation" />` to `src/BrewHouse/BrewHouse.csproj` (version already centrally pinned in `Directory.Packages.props`, matching every other `WolverineFx.*` package at `6.21.0`).
* **Rationale:** Confirmed live: the first deploy to actually reach a running `blazor-app.service` (after ADR 42's Postgres fix and ADR 43's `rsync` fix both cleared) crash-looped immediately with `System.InvalidOperationException: Wolverine is running in TypeLoadMode.Dynamic ... but no IAssemblyGenerator (Roslyn) is registered` — Wolverine's default `TypeLoadMode.Dynamic` compiles handler/middleware code at runtime and needs `WolverineFx.RuntimeCompilation` to do it, but core `WolverineFx` no longer bundles that compiler. `tests/BrewHouse.Tests/BrewHouse.Tests.csproj` already referenced this package directly (not transitively from the app project), so every test run — including the `Restore & Test` step that gates every deploy — exercised Wolverine with runtime compilation available and never caught that the actual app project didn't reference it at all. Same failure class as ADR 42/43: a real, always-present gap invisible until the app got far enough in a real deploy to actually start Wolverine's messaging host in production. `dotnet build` confirmed the reference resolves cleanly before pushing, to avoid burning another CI cycle on it. The alternative Wolverine offers (pre-generate code via `dotnet run -- codegen write` and set `TypeLoadMode.Static`, avoiding a runtime Roslyn dependency entirely) would fit this repo's "build once, execute exactly that artifact" discipline (ADR 11) better, but is a larger change (a new CI step plus a `Program.cs` change) — left as a follow-up, not bundled into this incident fix.

## ADR 45: Production Never Set `Realtime:HubBaseUrl`, So Every Page Self-Called the VIP's Nonexistent Port 80
* **Decision:** `src/systemd/blazor-app.service` now sets `Environment=Realtime__HubBaseUrl=http://localhost:5000`, matching the port `ASPNETCORE_URLS` already binds in the same file.
* **Rationale:** Confirmed live: the first deploy to get a running `blazor-app.service` (after ADR 42/43/44 all cleared) still 500'd on every real page — `curl -k https://10.10.110.199/` returned 500, while `/health` returned 200, isolating the failure to page rendering, not the app being down. The server log showed the actual exception: `System.Net.Http.HttpRequestException: Connection refused (10.10.110.199:80)`, thrown while rendering the root component. `SignalRBidsClient.cs` already anticipated exactly this failure mode in its own comment — `Realtime:HubBaseUrl` left unset derives the hub URL from `NavigationManager.BaseUri` (the incoming request's own scheme/host/port), which behind the Kemp VIP sends the SignalR connection back out through the VIP instead of staying in-process — and a direct TCP test confirmed `10.10.110.199:80` refuses connections outright (ADR 24 describes a `:80` VS forwarding to the real servers same as `:443`, but nothing is actually listening there). The PR preview stack (`docker-compose.pr.yml`) already sets `Realtime__HubBaseUrl=http://localhost:8080` for exactly this reason — production was simply never given the equivalent value in its systemd unit, a plain oversight, not a design gap; the config key, its default, and its documentation (`appsettings.json`, `CLAUDE.md`) already existed. Applied live: updated the unit on both web LXCs via `ansible-playbook-site.sh --limit web`, then `systemctl restart blazor-app.service` on each — `curl -k https://10.10.110.199/` now returns 200 with the actual rendered page. This is the fourth bug in a row (ADR 42/43/44/45) that was real and always present, each one only reachable once the previous one stopped masking it.

## ADR 46: Client-Side Access Gaps Found Auditing Every Homepage Link From a Real Browser
* **Decision:** No code or infra change here — this documents three real gaps found by loading every Homepage tile from an actual client browser (Chrome/Edge via the Claude in Chrome extension) rather than `curl` from an Ansible-managed LXC, plus where each is now tracked: (1) the capture/operator machine's own DNS resolver was never pointed at Technitium (`docs/11` §2 step 4 already documented this requirement — it just was never applied to this specific machine); (2) Portainer's 5-minute first-run security timeout had already expired, locking the instance until `docker restart ops-portainer-1`; (3) the hostname guessed at the time (`app.smartsoftwarecoffee.com`) has no public DNS record at all — confirmed via both `1.1.1.1` and `8.8.8.8`, not a local resolver artifact. **Correction, see ADR 47:** the parenthetical originally here claiming this was true "regardless of the Cloudflare Tunnel... being otherwise correctly configured" was wrong — the tunnel wasn't configured at all, that was simply undiscovered yet at the time this ADR was written.
* **Rationale:** Every prior "confirmed live" check on preview-app/Homepage reachability this session (`getent hosts`, `curl --resolve`, direct TCP tests) ran from an Ansible-managed LXC that already had correct DNS — none of it actually proved a human at a real workstation could reach these URLs, and in fact one couldn't, for a completely different reason (client DNS) than any of the server-side issues already fixed (ADR 42-45). Testing from the actual client surfaced all three gaps in one pass; none of the three needed a code change at the time — (1) and (2) were operational/setup gaps, and (3) turned out to need considerably more than a DNS record (ADR 47). Recorded here so this class of gap (server confirmed working ≠ client confirmed reachable) gets checked from a real browser going forward, not just from the fleet's own LXCs.

## ADR 47: Cloudflare Tunnel Was Never Actually Installed; Kemp's `:80` Health Check Used the Wrong HTTP Method
* **Decision:** Two independent, real gaps closed together while chasing ADR 46's "missing DNS record" finding to its actual root: (1) the `cloudflared` LXC (`10.10.110.5`) was a completely empty Terraform-provisioned shell — no `cloudflared` package, no config, no systemd unit, service not even present to be inactive. A tunnel named `brewhouse-homelab` already existed in Cloudflare's dashboard (created at some earlier point) with zero registered connectors — nothing had ever actually run `cloudflared` against it. Installed the Debian package (`docs/04 §2`'s existing apt-repo instructions) and ran `cloudflared service install <token>` using that tunnel's own token (retrieved from the Cloudflare dashboard's "Add a connector" panel), which brought it to a healthy 3-connection state immediately. (2) The tunnel's own ingress config revealed its Public Hostname was `homelab.smartsoftwarecoffee.com`, not `app.smartsoftwarecoffee.com` (ADR 46's guess) — routing plain `http://10.10.110.199` (port 80), not port 443. Fixing (1) alone surfaced a 502 at that hostname: Kemp's `Blazor-App-VIP-80` Virtual Service existed (contrary to earlier assumption in ADR 45/LAB-RUNBOOK that it was missing entirely) but had both real servers marked unhealthy, because its health check used a bare `HEAD /` — Blazor's root endpoint only allows `GET`/`POST` and returns `405` to `HEAD` (confirmed live via direct `curl -I -X HEAD`). Changed the check to `GET /health` (matching the working `:443` VS/LAB-RUNBOOK step 4.5's original intent) via the Kemp WUI; both real servers went healthy within one check interval. `ansible/inventory/group_vars/homepage.yml`'s `BrewHouse App` tile now points at `https://homelab.smartsoftwarecoffee.com` instead of the unconfigured `app.` guess.
* **Rationale:** ADR 46 correctly identified a symptom (no DNS record) but not the actual cause — the record was never going to matter, since nothing was listening on the tunnel side to receive traffic for it either way. Confirmed live end-to-end only after both fixes: `https://homelab.smartsoftwarecoffee.com/` now renders the real app (not a Cloudflare 502, not a Kemp "Down" VS) from a real client browser through Cloudflare → tunnel → Kemp → both web nodes. The `:80` VS's health-check misconfiguration is the more subtly dangerous of the two gaps — the VS existed, looked plausible in a config review, and would have kept silently failing indefinitely without ever producing an error that pointed at the actual mismatch (a `405`, not a timeout or connection failure); worth remembering next time a Kemp real-server health check is set up by hand rather than copy-configured from a known-working VS.

## ADR 48: blazor-web-01/02 Bumped to 2GB RAM / 1GB Swap After a Live Wedge Incident
* **Decision:** `blazor-web-01` (VMID 401, `10.10.110.101`) went completely unresponsive in production (2026-09-18) — reachable by ICMP, but SSH accepted the TCP handshake and then never sent its banner, the app's `:5000` port never completed a handshake at all, and even `pct exec` into the container's namespace from its Proxmox host (`pve4`) timed out, so no diagnosis was possible while it was wedged. Proxmox itself still reported the container `status: running` throughout. A `pct reboot` issued from the host hung too (`lxc-stop` itself had to be interrupted); the container only actually came back once its physical host (`pve4`) was restarted directly. Immediately after boot, load average was 16–26 on a 2-core LXC, and the box wedged again within minutes. `blazor-web-01`/`blazor-web-02` (`terraform/lxc.tf`) are bumped from `memory = 1024` (no swap configured) to `memory = 2048, swap = 1024` — applied to both nodes for parity, not just the one that actually wedged.
* **Rationale:** Root cause was never confirmed from logs — the box was unreachable by every diagnostic path (SSH, `pct exec`) while wedged, and the previous boot's kernel/journal log wasn't recoverable afterward (host was mid-restart) to check for an OOM-killer event. The one memory snapshot actually captured, moments after the box came back, showed no pressure (132MB used, 891MB available, 0 swap used out of 1024MB total) — pointing more toward the observed severe load average (CPU contention from every systemd unit, the PatchMon agent, Cockpit, and the .NET JIT all racing for 2 cores at once during boot) than classic OOM. Bumping RAM/swap is a precaution against the plausible cause, not a confirmed fix — 1GB was already thin for Kestrel plus the fleet-wide Cockpit (ADR 21) and PatchMon (ADR 34) agents sharing the box, and 0 swap meant any transient GC/JIT spike had zero headroom before either the OOM killer or outright thrashing kicked in. This is exactly the gap the still-unbuilt fleet-wide patch playbook (`LAB-RUNBOOK.md` §5) needs to guard against going forward — a reboot loop against a wedged host is not a substitute for understanding why it wedged.

## ADR 52: web-online Must Run `if: always()` — A Real Outage, Not a Hypothetical
* **Decision:** Both `deploy-blazor.yml`'s and `patch-fleet.yml`'s "Bring both web nodes back online" step (`uses: ./.github/actions/web-online`) now carries `if: always()`.
* **Rationale:** Confirmed live, in production, the first time `deploy-blazor.yml` ran against the freshly Terraform-recreated `blazor-web-03` (ADR 50): "Take both web nodes offline" is two sequential `scp` commands in one `run:` block — the first (to `blazor-web-04`) succeeded, the second (to `blazor-web-03`) failed with `Host key verification failed` (a genuinely new container has a genuinely new SSH host key; the runner's `known_hosts` still had the old one cached for that IP from the destroyed container). GitHub Actions stops a job on a failed step by default, so every step after that — including "Bring both web nodes back online" — was skipped. Result: `blazor-web-04`, the only node actually serving traffic, sat showing `app_offline.htm` to every real visitor (`/health` `200`, `/` `503`) with nothing left in the run to ever take it back down. Manually removed the file to restore service, then closed the actual gap: `if: always()` guarantees this step runs regardless of what failed earlier in the job, and it's safe to run unconditionally — `rm -f` and a health check are both idempotent even in the (also real) case where the site was never actually taken offline. `patch.yml`'s own web tier patching has the identical shape (offline → risky work → online) and the identical gap, so it got the same fix. The stale SSH host key that triggered this specific run is now cleared (`ssh-keygen -R`); it will recur any time a node's underlying container is destroyed and recreated at the same IP (any future Terraform replace), which is a separate, still-open question about whether to auto-refresh `known_hosts` in CI or keep clearing it by hand each time.

**Addendum, confirmed live the same day:** `if: always()` alone wasn't enough — the first real `Patch Fleet` run failed inside `web-online` itself, immediately after `patch.yml`'s reboot: `curl: (7) Couldn't connect to server` at `0 ms`. The one-shot health check ran before `blazor-app.service` had time to start listening on `:5000` post-reboot; the site was fine seconds later on its own, but the workflow had already failed the step (both nodes verified healthy by hand afterward - `if: always()` had already prevented a stuck-offline outage, this was a separate, narrower gap). `web-online` now retries each node's health check up to 10 times, 3s apart (30s budget), matching the retry budget `ansible/patch.yml`'s own health task already used for the identical post-reboot race on the Ansible side.

## ADR 68: Forward-Auth Routing Fixed, Confirmed Live — Access Gate Itself Still NOT Enforcing (Open)
* **Decision:** Two real, confirmed-live bugs fixed in the ADR 66 Caddy templates (`roles/caddy-forward-auth/templates/Caddyfile.j2`, `preview-host/templates/ops.caddy.j2`): (1) `forward_auth`'s upstream is a different hostname (`https://authentik.{{ internal_domain }}`) than the site itself, and Caddy rewrites the outbound `Host` header to match that dial address by default — Authentik never learned which app was actually being requested and 404'd the check every time. Fixed with `header_up Host {http.request.host}` inside the `forward_auth` block. (2) The whole site block is now wrapped in an explicit `route { }`, with a new leading `reverse_proxy /outpost.goauthentik.io/* ...` passthrough — both missing before, both present in Authentik's own official Caddy documentation template, and required for the OAuth callback that completes login to have anywhere to land. Separately, the embedded outpost's own `authentik_host`/`authentik_host_browser` config (`GET /api/v3/outposts/instances/<pk>/`) was blank — set to `https://authentik.{{ internal_domain }}` live via the API, which also explains an earlier-observed broken `http://localhost/application/o/authorize/...` redirect URL.
* **Still open, NOT fixed:** even with all of the above, a fully unauthenticated request (confirmed via `curl` with zero cookies from a separate process, AND via a real Chrome browser with a clean, verified-empty cookie jar) still gets waved straight through the auth check to the real backend app, instead of being redirected to Authentik's login flow. Ruled out as the cause, each confirmed live: (a) binding an explicit `require-authenticated-user` expression policy to the Application (no change); (b) `forward_single` mode instead of `forward_domain` (identical bypass, so it isn't domain-mode-specific); (c) `skip_path_regex` being empty and somehow matching every path (set to a deliberately non-matching regex, no change); (d) a stale/leftover session cookie from earlier manual testing (curl's request is provably cookie-free; the real browser's cookie jar was checked and contained no Authentik cookie). Until this is resolved, **these five apps are not actually access-gated** — Caddy/TLS/routing all work correctly, but anyone who can reach the URL gets straight through.
* **Rationale:** Found and fixed via the same "confirmed live" discipline as every other ADR here — Chrome browser testing (at the user's specific request, to rule out `curl` as a testing artifact) reproduced the identical bypass a stateless `curl` request showed, which is what gave confidence this is a real gap rather than a methodology error. Research into upstream GitHub issues turned up a cluster of open, unresolved proxy/outpost authentication bugs specific to the 2026.8.x release line (`goauthentik/authentik` issues #26125, #26076, #26270, among others) — none is an exact match for this specific symptom, but the pattern (multiple independent, still-open auth-path regressions clustered around this exact version) is strong circumstantial evidence this may be an upstream bug rather than a configuration gap, though that is not confirmed. Deliberately stopped guessing further at this point rather than continue an unbounded trial-and-error search; likely next steps for whoever picks this up are pinning to a different `authentik_version` known not to exhibit this, or filing/searching further for the exact upstream issue.
* **Also fixed as this app was cleaned up:** Homepage's `HOMEPAGE_ALLOWED_HOSTS` (env.j2) would have rejected the new Caddy front's Host header (`homepage.{{ internal_domain }}`, no port) even once auth is fixed — added. PatchMon's own `CORS_ORIGIN` (`patchmon.env.j2`, still `http://{{ ansible_host }}:{{ patchmon_port }}`) will similarly reject requests via `https://patchmon.{{ internal_domain }}` once the auth gate is closed — **not yet fixed**, tracked here as a known follow-up alongside the auth gate itself.

## ADR 71: ADR 68's "Anonymous Bypass" Root-Caused and Fixed — a Port in the Host Header
* **Decision:** `header_up Host` in every `forward_auth`/outpost-passthrough block (`roles/caddy-forward-auth/templates/Caddyfile.j2`, `preview-host/templates/ops.caddy.j2`) now sets a bare hostname (`authentik.{{ internal_domain }}`, no port) instead of `{http.request.host}` or Caddy's own default. **This closes ADR 68.** All five tier-2 apps are now confirmed-live actually access-gated, not just routed.
* **Rationale:** Found by reading Authentik's own Rust outpost source (`goauthentik/authentik`, `src/outpost/proxy/mod.rs`) after exhausting config-level guesses (documented in ADR 68). `ProxyOutpost::lookup_app(host)` is what selects *which* of the five providers should handle a given `forward_domain` request: it tries an exact host match first, then falls back to checking `host.ends_with(cookie_domain)` across every `forward_domain` provider. The `host` it checks is the **literal incoming HTTP `Host` header** of the connection Caddy makes to Authentik — and Caddy's own default, when the upstream is specified as a bare URL (`forward_auth https://authentik.{{ internal_domain }}`), sets that header to the **dial address including the port** (`authentik.brewhouse.internal:443`). `"authentik.brewhouse.internal:443".ends_with("brewhouse.internal")` is `false` — the trailing `:443` breaks the suffix match for every single provider. `lookup_app` returns `None`, `app_for_request` returns `None`, and the request silently falls through to Authentik's own **core backend** (the same process, embedded) instead of ever reaching the outpost's forward-auth logic (`check_auth`/`is_allowlisted`/`auth_start`) at all — which is why it read as an unconditional "let everything through": the auth check was never actually running. The core backend then just serves whatever its own Django URL router happens to return for an unrecognized path (a real page for some paths, a 404 for others), which is what produced the inconsistent, confusing symptoms chased throughout ADR 68 (200s, 404s, policy bindings and `skip_path_regex` changes that provably did nothing because none of that code was ever being reached). Confirmed live, methodically: manually reproducing Caddy's exact `X-Forwarded-*` headers via `curl` against Authentik directly got a correct `302` whenever the literal `Host` header curl sent omitted the port (curl's own default for a portless `https://` URL) and reverted to the broken behavior only when the `Host` header included `:443` — isolated by diffing Caddy's own debug-log dump of the real outbound request against a manually reconstructed one, header by header, until the port was the only remaining difference. Verified end-to-end afterward with a real browser: `https://patchmon.brewhouse.internal/` now correctly redirects to `Welcome to authentik! Log in to continue to PatchMon` (previously it went straight through, or — before this exact fix — attributed to the wrong provider's client, see caveat below).
* **Known caveat, not fixed here:** because all five providers share `cookie_domain: {{ internal_domain }}` with no host that exactly matches "authentik.{{ internal_domain }}", `lookup_app`'s suffix-match fallback is inherently ambiguous when several providers tie on domain length (all five do) — Rust's `HashMap` iteration order for that fallback loop is stable within one running process but arbitrary across restarts, so which provider's OAuth client/session cookie namespace actually "wins" for a first-touch login can vary per outpost restart. In practice this still requires a real login and still gates access correctly (confirmed live above), just not necessarily always attributed to the specific app the user first visited. A cleaner fix (giving each provider a truly unique `external_host` the literal Host header can exact-match, or accepting session-per-first-provider as the real cross-app SSO model) is a follow-up, not required to close the actual security gap ADR 68 opened.
  **Follow-up investigated (ADR 73's session) and deliberately not pursued further:** tried forwarding each app's own bare hostname (e.g. `header_up Host patchmon.{{ internal_domain }}` instead of the shared `authentik.{{ internal_domain }}`) specifically to hit `lookup_app`'s **exact**-match path instead of the ambiguous suffix-match fallback. Confirmed live this makes it *worse*, not better: the exact-match path returns the same bare `200` anonymous-bypass ADR 68 already fixed, even with fully correct `X-Forwarded-Host`/`Proto`/`Uri` headers alongside it — a separate bug in Authentik's exact-match code path, distinct from the port-in-Host bug this ADR fixed for the suffix-match path. The current shared-identity approach isn't a compromise being tolerated for convenience; it's the only one of the two `lookup_app` code paths that's actually confirmed to enforce authentication at all. Not investigating further validates ADR 68's fix was the right one to land and ship, rather than a symptom of a still-deeper problem.

## ADR 75: RabbitMQ OIDC Login Still Failed After ADR 73 — Three More Real Bugs, All Authentik-Side

* **Decision:** ADR 73 declared RabbitMQ's tier-1 OIDC "confirmed live" on the strength of the redirect-to-Authentik-login-prompt proof, but a real end-to-end login attempt (first one actually completed with real credentials this session, since a human — not the assistant — typed the password) surfaced three further, independent bugs, all in Authentik's own OAuth2 Provider object for RabbitMQ (`pk=11`), none in `rabbitmq.conf.j2` or the Ansible role, which were already correct:
  1. **Missing group membership**: `akadmin` wasn't a member of the `rabbitmq-administrator` group, so `auth_oauth2.scope_aliases` (ADR 73) had nothing to match and RabbitMQ rejected the token as unauthorized. Fixed by adding the user to the group. This is a per-user provisioning step, not a config bug — anyone who needs RabbitMQ admin access has to be placed in that group, same as any other Authentik-backed app.
  2. **CORS blocked the browser's own discovery fetch**: the Homepage tile (see below) pointed at RabbitMQ's raw `http://10.10.120.112:15672/`, not the Caddy-fronted `https://rabbitmq.{{ internal_domain }}` ADR 73 actually wired up — from that origin, the management UI's `fetch()` of Authentik's OIDC discovery document failed with a plain `TypeError: Failed to fetch`, which the browser reports identically for a network error and a CORS rejection, so it looked like the discovery endpoint was unreachable even though `curl` against it worked fine. Root cause: Authentik derives `Access-Control-Allow-Origin` from a provider's own `redirect_uris` list, which only had a path-suffixed callback entry (`.../js/oidc-oauth/login-callback.html`) — no bare-origin entry, so no origin was ever allow-listed for `fetch()`/XHR at all (full-page navigation isn't CORS-gated, which is why the OIDC *redirect* itself worked while the discovery *fetch* didn't). Fixed by adding a second `redirect_uris` entry with no path, just the origin.
  3. **Empty JWKS response**: even after fixing #2, RabbitMQ's own log (`/var/log/rabbitmq/rabbit@rabbitmq.log`, not journald — journald had nothing) showed `Failed to download signing keys from ".../jwks/": {error, empty_jwks_response}`. The provider had no `signing_key` assigned, so Authentik defaulted to symmetric HS256 signing (confirmed via the JWT header) — HS256 has no public key, so the JWKS endpoint correctly served `{}`. `rabbitmq.conf.j2`'s `auth_oauth2.issuer`-based verification (ADR 73) requires asymmetric RS256 to have anything to fetch. Fixed by PATCHing the provider's `signing_key` to Authentik's own self-signed `CertificateKeyPair`, switching it to RS256; confirmed live the JWKS endpoint then served a real RSA public key, and a subsequent real browser login (localStorage/sessionStorage cleared first, since the old HS256-era session was still cached) landed cleanly on the RabbitMQ dashboard as `akadmin` with no error.
  Separately, `ansible/inventory/host_vars/rabbitmq.yml`'s `homepage_service.href` still pointed at the raw `http://{{ ansible_host }}:15672` (the pre-ADR-38-pattern URL, never updated when ADR 73 stood up the Caddy TLS front) — fixed to `https://rabbitmq.{{ internal_domain }}`, matching the pattern ADR 38/66 already established for every other Caddy-fronted tile (PatchMon, Uptime Kuma).
* **Rationale:** User-reported, reproduced live via Chrome browser automation rather than asking the user to keep testing blind — the first report was against the stale Homepage URL, which made the symptom (discovery "not reachable") look like a server-side outage when `curl` from any trusted host showed the endpoint was fine; only testing from the actual failing origin in a real browser surfaced the CORS distinction between full-page navigation and `fetch()`. All three bugs are specific to *this* provider object, created manually via the same live-API pattern as every other tier-1/tier-2/tier-3 Authentik object this session (ADR 72/73/74) — none of Grafana/pgAdmin/Portainer/Infisical/Proxmox reported this symptom, plausibly because none of their client libraries do a browser-side JWKS `fetch()` the way RabbitMQ's `oidc-client-ts`-based management UI does; worth checking if any of those are ever reported broken, but not chased speculatively here without a live symptom.

## ADR 76: ADR 75's "None of the Others Reported This" Was Wrong — Grafana and pgAdmin Had Their Own Real Bugs Too

* **Decision:** ADR 75 speculated that Grafana/pgAdmin/Portainer/Infisical/Proxmox hadn't hit RabbitMQ's class of bug because their client libraries don't do a browser-side JWKS `fetch()`. A real login attempt against each (screenshots supplied by the user, not narrated) proved that guess wrong for two of the five — both genuine, independent, Authentik-side bugs, found the same way as ADR 75's:
  1. **pgAdmin: identical empty-JWKS bug as RabbitMQ.** The pgAdmin OAuth2 Provider (`pk=10`) also had no `signing_key` assigned, defaulting to HS256. pgAdmin's `config_local.py` (ADR 73) points Authlib at `OAUTH2_SERVER_METADATA_URL`, and Authlib fetches `jwks_uri` from that discovery document to verify the ID token signature — against an empty `{}` JWKS response, Authlib's own code does an unguarded `response['keys']`, producing pgAdmin's login page error `errormsg: "'keys'"` (a raw Python `KeyError: 'keys'` surfaced to the user, not a rendered message). Fixed identically to RabbitMQ: PATCHed `signing_key` to Authentik's self-signed `CertificateKeyPair`, confirmed live the JWKS endpoint now serves a real RS256 key.
  2. **Grafana: the step-ca CA-trust gap ADR 73 already knew about, just never applied here.** Grafana's login page showed a generic "Login failed — Failed to get token from provider"; `journalctl -u grafana-server` on `observability` had the real error: `tls: failed to verify certificate: x509: certificate signed by unknown authority` on Grafana's own server-side POST to `https://authentik.{{ internal_domain }}/application/o/token/`. ADR 73 found and fixed this exact gap for RabbitMQ/pgAdmin/Proxmox (each app's own HTTP client needs step-ca's root explicitly trusted — Caddy-fronted apps get it for free from their Caddy front, direct-HTTPS-calling apps don't), but Grafana (ADR 72) was built *before* that pattern was discovered and never got the same treatment. `roles/observability/tasks/main.yml` gained the same `copy` root cert + `update-ca-certificates` task pair RabbitMQ/pgAdmin already had, gated on `grafana_oidc_client_id is defined`. Not yet re-converged against the live host as of this ADR landing (pushed to `main`, `ansible-converge.yml` will apply it on its next run) — unlike the pgAdmin/RabbitMQ signing-key fixes, this one needs an actual CA-trust-store + service-restart change on the host, which goes through the normal converge pipeline rather than a live API PATCH.
* **Rationale:** The user tested Grafana and pgAdmin's real login flows by hand and supplied screenshots rather than description, which is what actually surfaced these — both errors were generic enough ("Login failed", a raw Python dict dump) that guessing the cause from the symptom alone would have been unreliable; reading each app's own server-side log was necessary both times, same discipline as ADR 75's RabbitMQ investigation. The corrected finding: **every tier-1 app that makes its own outbound HTTPS call to Authentik needs step-ca's root trusted, full stop** — this is now true for all six (RabbitMQ/pgAdmin/Proxmox via ADR 73, Grafana via this ADR); Portainer's and Infisical's own connection steps are still pending manual completion (ADR 73) so whether they'll hit the same gap is unconfirmed, not ruled out.

## ADR 79: Bids Were Never Actually Processed — Wolverine Codegen Failed on `AuctionDbContext`

* **Decision:** `MessagingTransportConfigurator.ConfigureDurability` now calls `options.CodeGeneration.AlwaysUseServiceLocationFor<AuctionDbContext>()`.
* **Rationale:** Confirmed live: with ADR 78 fixed, bid clicks reached the server but still did nothing visible — no client-side error, because `IMessageBus.PublishAsync` is fire-and-forget from the browser's perspective. `journalctl -u blazor-app.service` on `blazor-web-04` showed the real failure: `fail: Wolverine.Runtime.WolverineRuntime[0]` / `System.InvalidOperationException: Frame chain is being re-arranged...`, thrown from `Wolverine.Runtime.Handlers.HandlerGraph.resolveHandlerFromChain` the instant a `ProcessBidMessage` needed dispatching — Wolverine never got as far as calling `ProcessBidHandler.Handle`. Reproduced in seconds, without Docker or any live infra, via Wolverine's own `dotnet run -- codegen test` CLI command (already exposed for free by this app's existing `RunJasperFxCommands(args)` in `Program.cs`), which surfaced the precise, much clearer root cause: `Wolverine.Configuration.InvalidServiceLocationException` — `AddDbContext<AuctionDbContext>` registers `DbContextOptions<AuctionDbContext>` via an opaque lambda factory (`EntityFrameworkServiceCollectionExtensions.CreateDbContextOptions`) that Wolverine's code generator can't compose inline into the handler's generated dispatch method, and falling back to service location for a dependency it can't statically construct has been disallowed by default since Wolverine 6.0. Fixed per Wolverine's own codegen guide (`wolverinefx.net/guide/codegen.html`), which documents `AlwaysUseServiceLocationFor<T>()` as the narrow, targeted escape hatch for exactly this case — "helpful for EF Core `DbContext` types that might require some runtime configuration to construct themselves" — rather than restructuring the DbContext registration or taking on `WolverineFx.EntityFrameworkCore` for a transactional-outbox integration this app doesn't otherwise need (see ADR 07's own note in `MessagingTransportConfigurator.cs`). Same masking pattern as ADR 44: `tests/BrewHouse.Tests/ProcessBidHandlerTests.cs` calls `ProcessBidHandler.Handle(...)` directly as a plain static method — a real, valid unit test of the handler's *logic*, but one that never routes through Wolverine's generated dispatch pipeline, where the actual failure lived. **This means bid placement had never worked end-to-end in production, from the feature's first deploy through today** — every green test and every "✅ built" status note in `SERIES.md`/`DEMO-AUDIT.md` was true of the handler in isolation and false of the running app. Confirmed fixed live: `dotnet run -- codegen test` now reports `Success!`, and a real browser click moved "Cron Job Huila" from $375.00 to $875.00 with the change confirmed in `journalctl` (`Processed bid of ...`) and broadcast back to the browser.

## ADR 80: Web Nodes Never Shared Data Protection Keys — a Second, Separate Circuit Killer

* **Decision:** `Program.cs` now calls `builder.Services.AddDataProtection().PersistKeysToStackExchangeRedis(...).SetApplicationName("BrewHouse")`, pointed at the same Garnet instance as the cache/SignalR backplane (its own lazy connection, opened on first use rather than at process start, so CLI-only invocations like `codegen test`/`db-apply` still don't require Garnet to be reachable).
* **Rationale:** Confirmed live while re-verifying ADR 79 in a real browser: roughly two of every three fresh page loads against the Kemp VIP threw a client-side `Circuit host not initialized` / `No Connection with that ID: Status code '404'` error and displayed the app's own `#blazor-error-ui` banner, even though the earlier long-polling fallback test had looked clean. In the same change, `Microsoft.AspNetCore.DataProtection.StackExchangeRedis` 10.0.0 pulled a vulnerable `System.Security.Cryptography.Xml` 10.0.0 (several known high-severity CVEs, flagged by `dotnet build`'s NU1903 warning) — overridden to `10.0.12` in `Directory.Packages.props`, the same direct-override pattern this repo already uses for the test project's AngleSharp dependency.

## ADR 93: Kemp SubVS Persistence Was `None`, Not Inherited From the Parent VIP — Sticky-Session Gap Broke BrewHouse Circuits Through the LB

* **Decision:** On the LoadMaster (`10.10.10.199`), the `:443` VIP's SubVS (`Blazor-App-VIP`, Id:1 → SubVS Id:3 — the object that actually holds both real servers and does the round-robin) had its Persistence Options → Mode changed from `None` to `Source IP Address`, timeout `6 Minutes`. The plain `:80` VIP (`Blazor-App-VIP-80`, Id:2, real servers attached directly, no SubVS) got the same Source IP / 6-minute persistence applied for consistency, though it wasn't implicated in the reported bug.
* **Rationale:** User report: hitting each Blazor Server backend directly (`blazor-web-03`/`04`, port 5000) showed no error, but the same app through Kemp (`https://homelab.smartsoftwarecoffee.com/`) failed intermittently. Reproduced live via Chrome browser automation — a page reload against the real VIP threw a client-side console error: `Failed to start the transport 'WebSockets': ... the connection ID is not present on the server ... If you have multiple servers check that sticky sessions are enabled`, followed by an automatic fallback to long polling; a screenshot the user supplied independently showed the same failure from the other side, the app's own `#blazor-error-ui` "An unhandled error has occurred" banner. Investigating the LoadMaster config directly (rather than assuming a generic "add sticky sessions" fix) found the actual gap was subtler than a missing setting: the `:443` VS's own top-level Persistence Options already read `Source IP Address` — but that field is vestigial once a SubVS is attached, since the SubVS is what actually holds the real servers and performs scheduling. That SubVS (Id:3, `10.10.110.101:5000` + `10.10.110.102:5000` under `round robin`) had its own, independent Persistence Mode set to `None`, silently overriding the parent. Every request — including the WebSocket upgrade that follows a SignalR negotiate call — could land on either backend independent of which one issued the negotiate response.
  Checked `src/BrewHouse/Program.cs` directly (via the devops LXC's own checkout of this repo) to validate the fix rather than guess at a timeout: `AddServerSideBlazor` sets `DisconnectedCircuitRetentionPeriod = TimeSpan.FromMinutes(3)`, `KeepAliveInterval = 15s`, `HandshakeTimeout = 30s`. This is a distinct failure mode from ADR 80's Data Protection fix — ADR 80 covers a prerendered page's encrypted state payload being undecryptable if the interactive circuit resumes on a *different* node than the one that rendered it; this bug is SignalR's own negotiate→connect pairing, which the Garnet-backed SignalR backplane already wired per ADR 08 only fans messages across once a connection exists — it never routes a specific client's negotiate response to a specific node's WebSocket accept. No code-side change makes that pairing node-agnostic short of replacing self-hosted SignalR with a connection-routing-aware service (e.g. Azure SignalR Service); sticky sessions at the LB are the correct and only fix for this class of failure with the current architecture — confirmed by asking the same question in reverse (looked for a code fix before settling on the LB one) rather than assuming there wasn't one.
  Persistence timeout set to 6 minutes as roughly 2x the app's own 3-minute circuit retention: enough headroom to survive a normal reconnect blip (tab backgrounded, brief Wi-Fi drop) without pinning a client's source IP to one backend meaningfully past the point the app would have discarded the circuit anyway, which would otherwise skew round-robin distribution for no benefit. Both VSs' Idle Connection Timeout were left at Kemp's default (blank → 660s), comfortably longer than the app's 15-second SignalR keep-alive interval, so no change needed there. Confirmed fixed live: repeated reloads against the real Kemp VIP afterward showed a clean WebSocket connect every time, no transport error, no long-polling fallback.

## ADR 96: BrewHouse Traces Were Never Reaching Tempo — the Web Tier's Firewall Never Got an OTLP Exception

* **Decision:** New `unifi_firewall_policy.web_to_observability_otlp` (`terraform/unifi.tf`) allows VLAN 110 (Web) → `10.10.130.118:4318` tcp (Alloy's OTLP/HTTP receiver), added to `drop_web_to_mgmt`'s `depends_on` list alongside the existing `web_to_infisical`/`web_to_patchmon`/`web_to_homepage` exceptions it's modeled on.
* **Rationale:** User report, following ADR 95's DNS fix: bids had been placed on the live app, but Grafana showed no trace at all. Checked Tempo's own API directly rather than guessing (`curl .../api/search` → `{"traces":[],...}`, tag schema showing only Tempo's built-in fields, no real span attributes ever ingested) - confirmed this wasn't a stale-data or retention question, nothing has ever actually landed. `tempo`/`alloy`/`grafana-server`/`loki` were all healthy and listening (`journalctl -u alloy` showed nothing at all, not even errors - consistent with never receiving a connection attempt in the first place). Root cause found by testing the actual network path rather than the application: `curl --max-time 5 http://10.10.130.118:4318/v1/traces` from `blazor-web-04` timed out completely (exit 28, `HTTP 000`) - no TCP handshake at all, not an application-layer rejection. `docs/05-unifi-network-isolation.md`'s own documented policy table confirms why: `Block | VLAN 110 (Web) | VLAN 130 (Management) | Any` exists with only three narrow exceptions carved out ahead of it (Infisical `:8080`, PatchMon `:3000`, Homepage `:3000`, each already documented as its own ADR 29/37/47) - nobody ever added a fourth for Alloy's OTLP port when `ansible/roles/observability` was built. `Program.cs`'s `OTEL_EXPORTER_OTLP_ENDPOINT=http://10.10.130.118:4318` and `UseOtlpExporter()` were both present and correctly configured the whole time; this is why the app itself never surfaced any error - OTLP span export is fire-and-forget by design (the SDK doesn't fail a request because a trace couldn't be exported), so a completely silent network drop was indistinguishable from "working" until someone actually went looking for a trace in Grafana and found none, exactly the gap `LAB-RUNBOOK.md`'s own verification-checklist step for this shot exists to catch.
  Same known `unifi_firewall_policy` ordering gotcha as every prior `web_to_*` exception (`docs/05`'s own note, hit for `web_to_infisical`/`web_to_patchmon` before this): the controller assigns `index` itself, read-only, and a brand-new allow rule is appended *after* an already-existing `drop_web_to_mgmt`, regardless of `depends_on` (which only orders Terraform's own API calls, not the controller's evaluated rule order) - so creating this rule alone would still leave it unreachable. Needs the same documented follow-up as before: once this rule is applied, `terraform apply -replace=unifi_firewall_policy.drop_web_to_mgmt` to force the drop rule to a fresh, later index.
* **Not yet applied live:** unlike ADR 93-95's DNS fix, this change was **not** also applied out-of-band ahead of `terraform apply` - a new cross-VLAN firewall exception is a meaningfully more security-sensitive change than a DNS resolver setting, and belongs behind the same `homelab` environment approval every other Terraform change goes through (ADR 22), without a live workaround shortcutting it first. `terraform plan` confirms the change itself is clean (`1 to add, 16 to change` combined with ADR 95's pending DNS fix, `0 to destroy`) and ready for review; traces will start appearing in Tempo/Grafana once `terraform apply` (this rule, then the documented `-replace` follow-up) actually runs.

## ADR 98: `local_file.ansible_inventory` Showed a Phantom Diff on Every Plan — Non-Deterministic Map Iteration Order

* **Decision:** `terraform/outputs.tf`'s `web_hosts` list comprehension now iterates `sort(keys(local.lxcs))` and indexes back into the map (`local.lxcs[name]`), instead of iterating `local.lxcs` directly (`for name, cfg in local.lxcs`).
* **Rationale:** User asked why a freshly-approved `terraform.yml` run (ADR 97) found a plan diff at all when the immediately-prior apply had just finished successfully. Traced precisely rather than assumed: the prior apply's own log confirmed `Apply complete! Resources: 2 added, 16 changed, 0 destroyed` - real infrastructure (ADR 95's DNS block, ADR 96's firewall rule) was genuinely applied. The new run's plan showed exactly `1 to add, 0 to change, 0 to destroy`, and that one add was `local_file.ansible_inventory` - the *same* resource the prior apply had *just* created (`Creation complete`, a real content-hash id logged). A `local_file` resource's `id` is its content's hash; Terraform reported a pure `+ create` (not `~ update`), meaning its own state genuinely didn't recognize the file as existing/matching at plan time. Root cause: `web_hosts = [for name, cfg in local.lxcs : {...} if contains(cfg.tags, "web")]` is a `for` expression producing a **list** (not an object via `=>`) by iterating a **map** directly - Go/HCL gives no ordering guarantee for that combination, so the two web hosts (`blazor-web-03`/`-04`) could render in either order between separate `plan`/`apply` invocations with zero actual config changes, shuffling the rendered YAML's byte content (and therefore the file's content-hash `id`) unpredictably. `lxc_ips` (an object output, `=>`) and `infra_hosts` (iterates a literal list, not a map) were checked and confirmed not to share this problem - `web_hosts` was the only affected comprehension.
* **Confirmed live:** `terraform validate` passes; `terraform plan` against the real, already-converged infrastructure reports `No changes. Your infrastructure matches the configuration.` - both the currently-applied file content and the newly-sorted code path now agree, closing the gap this session's own pipeline redesign (ADR 97) surfaced. Answers the user's actual question directly: the new pipeline did not redundantly re-touch any real DNS or firewall resource - this was a real, if harmless, Terraform footgun already latent in `outputs.tf`, and ADR 97 catching it (versus the old two-workflow setup, where nobody was necessarily comparing two consecutive plans closely enough to notice) is itself evidence the redesign is working as intended.

## ADR 99: OTLP Traces Still Weren't Reaching Tempo After the Firewall Fix — Missing `OTEL_EXPORTER_OTLP_PROTOCOL`

* **Decision:** `ansible/roles/observability` pushes a second Infisical secret, `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`, alongside the existing `OTEL_EXPORTER_OTLP_ENDPOINT` push - same `infisical-secret` role, same `when: infisical_project_id is defined` gate. The Infisical Agent renders every project-root secret into `/etc/brewhouse/brewhouse.env` unconditionally (`listSecrets ... "/"` in `agent-config.yaml.j2`, no allowlist), so no other change is needed for it to reach the web tier.

## ADR 102: Authentik-Provisioned Grafana User Was Permanently Stuck on Viewer — No Role Mapping Configured

* **Decision:** `ansible/roles/observability`'s Grafana OIDC env block gains `GF_USERS_AUTO_ASSIGN_ORG_ROLE=Editor`, alongside the existing `GF_AUTH_GENERIC_OAUTH_*` settings (ADR 72).
* **Rationale:** Discovered while getting a real trace on screen for the channel trailer: signing into Grafana via "Sign in with Authentik" worked end-to-end (ADR 72/76 already confirmed the OIDC flow itself), but navigating to Explore silently bounced back to `/` - Grafana's own access-denied redirect pattern. `GET /api/org/users` (as the local `admin` account) showed the Authentik-provisioned user (`admin@brewhouse.internal`, `isExternallySynced: true`) pinned at `role: "Viewer"`. Root cause: no `GF_AUTH_GENERIC_OAUTH_ROLE_ATTRIBUTE_PATH` (or equivalent group-claim mapping) was ever configured, and Grafana's default fallback role for an externally-synced OAuth user with no matching claim is `Viewer` - re-applied on **every** login, not just the first, so a one-off manual promotion via the API would have been silently reverted the next time that account signed in. Viewer lacks Explore access by default (requires Editor+), so this made the entire "place a bid, see a real trace" workflow (`LAB-RUNBOOK.md`'s own verification step) unreachable through the intended SSO path - worked around in the moment by using the local `admin` account instead, but that's not the account anyone would actually use going forward.
  `GF_USERS_AUTO_ASSIGN_ORG_ROLE` isn't just an initial-signup default in current Grafana - with no `role_attribute_path` match, it's what every OAuth login re-syncs to, so setting it fixes the already-existing stuck account as well as any future one, no manual per-user promotion needed. `Editor`, not `Admin`: enough for Explore and dashboard editing without also granting server-wide user/org administration to whichever Authentik account happens to sign in - `GF_AUTH_GENERIC_OAUTH_ALLOW_SIGN_UP=true` means any valid Authentik login can auto-provision a Grafana account, so the default shouldn't be the most privileged one.
* **Not yet confirmed live as of this ADR landing** - needs the normal `ansible-converge.yml` path to update `/etc/default/grafana-server` and restart `grafana-server` (the `blockinfile` task already has a `notify: restart grafana-server` handler, so no additional step needed once converged), then a fresh Authentik-SSO login to Grafana to confirm Explore is reachable without the local admin workaround.

## ADR 105: Every Bid Showed Up as an Isolated Single-Span Trace — Wolverine's Own Tracing Was Never Registered

* **Decision:** `Program.cs`'s OpenTelemetry `WithTracing` builder gains `.AddSource("Wolverine")`, alongside the existing `.AddSource("Npgsql")`.
* **Rationale:** User asked for a richer, nested trace for the channel trailer's Grafana shot. Checked across 200 recent traces in Tempo (2-hour window) before assuming a code fix was even the right call: the maximum span count anywhere was 2 (`GET /health` checks) - every real app operation, including a bid click, showed up as its own isolated single-span root trace, with no parent/child linkage between related operations (`Route /`, `Circuit ...`, `StartCircuit`, and `GET /_blazor` from one page load all appeared as four *independent* traces, not one). Investigated Wolverine's own tracing support directly rather than guessing at a fix, the same way ADR 91's CritterWatch integration verified real API shapes: no `Wolverine.dll` build artifact existed on the devops checkout, so installed `ilspycmd` as a global dotnet tool and decompiled the installed `WolverineFx` 6.29.1 package from the NuGet cache. Found `Wolverine.Runtime.WolverineTracing.ActivitySource`, a `System.Diagnostics.ActivitySource` literally named `"Wolverine"`, and `StartEnvelopeActivity` explicitly using `envelope.ParentId` (populated from the W3C `traceparent` header Wolverine already attaches to outgoing messages) to parent a handler's span under whatever trace initiated it - full distributed-tracing support already built in, including automatic context propagation across the RabbitMQ transport boundary. * **Not yet confirmed live as of this ADR landing** - `dotnet build` confirms the change compiles cleanly; needs the normal `deploy-blazor.yml` path (tests, publish, both web nodes, `homelab` environment approval) to actually ship, then a fresh bid placed and checked in Tempo/Grafana to confirm a real multi-span waterfall (the "Event onclick" publish span, a Wolverine send span, a Wolverine handle span in `ProcessBidHandler`, and its Postgres write nested underneath) now renders as one linked trace instead of several disconnected ones.

## ADR 108: RabbitMQ Fd Exhaustion Root-Caused to `/health`, Log Growth Capped — and Vault Secrets No Longer Rendered Into App Environments

* **Decision:** Three fixes for the outage ADR 107 diagnosed. (1) `src/BrewHouse/Services/RabbitMqHealthConnection.cs`: the `/health` RabbitMQ check now reuses ONE shared, lazily-created AMQP connection (disposed and replaced only if closed) instead of opening a new one per probe. (2) `roles/rabbitmq`: `LimitNOFILE` raised 32768 → 65536 via a systemd drop-in, and RabbitMQ's own size-based log rotation enabled (`log.file.rotation.size` 50 MiB x `count` 5, in `/etc/rabbitmq/conf.d/10-logging.conf`) - a drop-in, not `rabbitmq.conf`, because that file is only written when OIDC is configured. (3) Infisical secrets are split into per-service folders - `/brewhouse` (the 5 keys `src/BrewHouse` reads), `/critterwatch` (its 2), `/admin` (vault-only human credentials, readable by no Agent) - and `roles/infisical-agent` renders ONLY its consumer's `infisical_agent_secret_path`. `roles/infisical-secret` takes an `infisical_secret_path` (and ensures the folder exists, so a rebuilt Infisical works), every push site names its folder, and `ConnectionStrings__messaging` is pushed to both consumers' folders.
* **Rationale:** (1) Confirmed live: every `blazor-app` process opened a new AMQP connection with 0 channels exactly every 9 s (Kemp's health-check interval) and never closed it - 27→32 established connections per node in 40 s, RabbitMQ at 89→100 fds and climbing. `AspNetCore.HealthChecks.Rabbitmq` 9.0.0 calls the supplied factory on every check and doesn't dispose the result; the old `_ => new ConnectionFactory{…}.CreateConnectionAsync()` therefore leaked one connection per probe (~9,600/node/day against a 32768 limit). Handshake-timeout errors from only the two web nodes' IPs show the same leak in the rotated logs back to at least 2026-09-13. (2) The raised limit is headroom only; the leak fix is the cure, and the log cap is what stops a repeat from filling the root disk (a 5.7 GB single file had; the weekly logrotate job never fired in time). (3) Confirmed live: `critterwatch.env`, and both web nodes' `brewhouse.env`, each held 11 keys including `DEVOPS_LXC_ROOT_PASSWORD`, `PORTAINER_ADMIN_PASSWORD`, `PGADMIN_LOGIN`, `TECHNITIUM_ADMIN_PASSWORD` and `HOMEPAGE_AUTH_PASSWORD`. Cause: the Agent template did `listSecrets … "/"` with no filter, while other roles (and manual `store-secret.yml` runs) deliberately push human-facing admin credentials to that same root path as a vault - and `EnvironmentFile=` puts everything in the process environment, including the internet-facing web tier's. Live migration done 2026-10-06: folders created and all 12 values copied and hash-verified against the root originals; the originals at `/` are deliberately left until each consumer has its own scoped identity, then should be deleted.
* **Isolation boundary = a project, not a folder:** the free plan rejects custom (path-scoped) roles and IP binding, and built-in roles are project-wide - so each runtime consumer gets its OWN Infisical project (`BrewHouse Web`, `BrewHouse CritterWatch`) with a viewer-only identity (`brewhouse-agent`, `critterwatch-agent`); `/admin` stays in the main project. Roles resolve `infisical_project_ids.<target>` (falling back to a `/<target>` folder in the main project until it is set). Creating projects/org identities needs an org admin, and a project-scoped identity cannot join other projects, so an org-level `brewhouse-provisioner` (Admin on all three) replaces `HomeLab Provisioner`. Automated by `ansible/files/bootstrap-infisical.py` (ADR 112; was finish-infisical-split.py); full procedure and rebuild order in `docs/13-infisical-secrets.md`. Roll-out ends with deleting the root-level copies and retiring `HomeLab`. Both Ansible changes are unapplied until the next converge, and an already-running app keeps its old environment until restarted. Rotate the five exposed vault-only credentials if the web tier's exposure window matters to you.

## ADR 124: CritterWatch Telemetry Queue Has No Dead-Letter Exchange — Expired Status Updates Filled the Dead-Letter Queue

* **Decision:** The `critterwatch` RabbitMQ queue is declared without a dead-letter exchange on both sides: BrewHouse's sender (`MessagingTransportConfigurator`, `Queues["critterwatch"].DeadLetterQueue = null`) and the console's listener (`src/CritterWatch/Program.cs`, `ListenToRabbitQueue("critterwatch").DisableDeadLetterQueueing()`). Every other queue keeps Wolverine's default `wolverine-dead-letter-queue`.
* **Rationale:** Found 2026-10-13: after the rebuild `wolverine-dead-letter-queue` held 812 messages and then 1,545 forty minutes later (~18 a minute), while Wolverine's own Postgres dead-letter table was empty and no bid had failed. Peeking the queue showed every message was a `Wolverine.CritterWatch.Messages.Outbound.ServiceUpdates` that had died with `x-first-death-reason: expired`: BrewHouse reports status to the console every few seconds with a ~45 s expiry, CritterWatch was not deployed (nothing consumed the queue, ADR 121), and Wolverine gives every queue the transport-wide dead-letter exchange, so each expired update was routed there. Telemetry has no value once stale, so the right outcome for an expired update is to drop it. Both sides must agree because RabbitMQ rejects a queue redeclare with different arguments (`PRECONDITION_FAILED`).
* **Live rollout:** an existing `critterwatch` queue carries the old arguments, so it must be deleted once (`rabbitmqctl delete_queue critterwatch`, telemetry only) before the new BrewHouse starts; a rebuilt broker has no queue and needs nothing. The messages already in `wolverine-dead-letter-queue` are stale telemetry and were purged once with `rabbitmqctl purge_queue wolverine-dead-letter-queue`; the dead-letter page (ADR 125) covers Wolverine's own persisted dead letters (failed handlers), not this broker queue.

---
